              A Challenge-Response Authentication Protocol
                       with an Initiator Marker
                       draft-famed-crxor-imk-00


Abstract

   This document specifies CR-XOR-IMK, a two-flow challenge-response
   authentication protocol intended for point-to-point links between
   two endpoints that already share a long-term symmetric key.  The
   initiator's flight carries an explicit constant marker octet
   string in addition to the challenge nonce, allowing the responder
   to filter out flights that do not match the expected protocol
   profile.  The responder's flight returns a hash tag and the
   responder nonce.

1.  Introduction

   CR-XOR-IMK provides a compact mechanism by which an initiator
   verifies that a peer holding a pre-shared key is reachable and
   currently active.  The first flight carries the initiator's
   challenge nonce together with a fixed constant marker, declared
   in this document as "Init", that the responder is required to
   match before it engages with the protocol.  The second flight
   contains the hash tag and the responder nonce.

   The marker simplifies multiplexing on hosts that may receive
   protocol-shaped traffic of more than one variety on the same
   transport.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   H is a cryptographic hash function.  XOR denotes bitwise
   exclusive-or applied to equally sized octet strings.  <a, b>
   denotes the concatenation of a and b in the order shown.  na is
   the initiator nonce, nb is the responder nonce, and k is the
   shared symmetric key.  The role names I and R denote the
   initiator and the responder.  IMK denotes the constant octet
   string "Init", encoded according to Section 4.


3.  Protocol Overview

   CR-XOR-IMK runs in a single round trip:

      Initiator                                       Responder
          |                                                |
          |                  na, "Init"                    |
          |----------------------------------------------->|
          |                                                |
          |        H(na XOR k XOR nb), nb                  |
          |<-----------------------------------------------|
          |                                                |
          |  verify H tag                                  |
          |                                                |

   The initiator generates a uniformly random nonce na of length
   L_n, transmits na together with the constant IMK, and waits for
   the responder's reply.  The responder, upon receiving the first
   flight, MUST check that the trailing field equals IMK; if it does
   not, the flight is dropped without further processing.  The
   responder then generates a fresh nonce nb of length L_n, computes
   t = H(na XOR k XOR nb), and transmits <t, nb>.  The initiator
   recomputes t' from the values it holds and compares it to the
   received tag.


4.  Message Format

      struct {
          opaque  challenge[L_n];
          opaque  marker[L_m];
      } InitiatorFlight;

      struct {
          opaque  tag[L_h];
          opaque  response_nonce[L_n];
      } ResponderFlight;

   The constant IMK consists of the four ASCII octets {0x49, 0x6e,
   0x69, 0x74}, that is, the string "Init".  L_m is fixed at four.


5.  Processing Rules

   The shared key k MUST be established out of band.  k MUST be
   drawn uniformly at random and MUST be kept secret to both
   endpoints.

   An implementation acting in the role I performs the following
   steps.

   1.  Generate a fresh nonce na of length L_n.  na MUST NOT be
       reused across runs.

   2.  Transmit InitiatorFlight{ challenge = na, marker = IMK }
       to the responder and retain na in protocol state.

   3.  Wait for a ResponderFlight.  On receipt of <tag, nb>:

       a.  Verify that nb has length L_n and is non-zero.

       b.  Compute t' = H(na XOR k XOR nb).

       c.  Compare t' to tag in constant time.

       d.  If t' equals tag, declare the responder authenticated;
           otherwise abort.

   4.  Discard na after step 3.

   An implementation in role R, on receipt of an InitiatorFlight,
   MUST verify that the marker field equals IMK; otherwise the
   flight is dropped.  The responder MUST verify that na has length
   L_n and is non-zero, generate a fresh nb of length L_n, compute
   t = H(na XOR k XOR nb), and transmit <t, nb>.


6.  Security Considerations

   CR-XOR-IMK is designed to convince the initiator that the holder
   of k has reacted to the current challenge.  When the verification
   at step 5.3.c succeeds, the initiator can conclude that the
   responder has been active at some point in time and is in
   possession of k.  This property is sometimes referred to as
   aliveness of the responder.

   The marker IMK is not part of the cryptographic input to H and
   does not by itself contribute to the authentication guarantee.
   It is intended solely as a transport-layer profile selector, and
   implementations should not rely on it for security purposes.

   The hash function H provides the cryptographic barrier against
   forgery of the responder flight.  H MUST be selected so that the
   work factor of preimage and collision attacks exceeds the
   lifetime value of k.

   The non-zero check on the nonces removes a degenerate case in
   which an attacker submits the all-zeros nonce; without the check,
   the algebraic identity x XOR x = 0 could be exploited to drive
   the hash input into a state that is independent of one of the
   nonces.

   Implementers should be aware that the construction H(na XOR k
   XOR nb) is bilinear with respect to its operands.  An active
   attacker that observes one valid responder flight <t, nb> for a
   challenge na' (after sending IMK on its behalf), and that is in
   a position to reroute traffic, can choose a fresh challenge na
   for an honest initiator and deliver the crafted response_nonce
   nb' = na XOR na' XOR nb together with the originally observed
   tag.  Under these circumstances the initiator's tag check
   succeeds even though the responder did not react to na.
   CR-XOR-IMK therefore does not provide agreement on the
   per-session parameters; it provides aliveness of the entity
   holding k, and nothing stronger.

   Deployments that need agreement on session parameters MUST
   compose CR-XOR-IMK with an additional layer that binds the
   verified exchange to specific session identifiers.

   Compromise of k breaks all guarantees of CR-XOR-IMK, both for
   past and future runs.  Implementations SHOULD provide a
   mechanism to rotate k.

   na and nb appear in cleartext on the wire and MUST NOT carry
   implicit information about the endpoints.  Deployments operating
   over open networks SHOULD rate-limit incoming InitiatorFlights
   at a lower layer.
