              A Challenge-Response Authentication Protocol
                       with an Initiator Audit Tag
                       draft-famed-crxor-iaudit-00


Abstract

   This document specifies CR-XOR-IAudit, a two-flow challenge-
   response authentication protocol between two endpoints that
   already share a long-term symmetric key.  The initiator computes
   a local audit tag derived from its challenge nonce and stores it
   in an internal log; the audit tag does not appear on the wire
   and is not part of the protocol's cryptographic verification.

1.  Introduction

   CR-XOR-IAudit provides a compact mechanism by which an initiator
   verifies that a peer holding a pre-shared key is reachable and
   currently active.  In addition to the basic two-flight challenge-
   response exchange, the initiator derives a local audit tag

         tag_audit_I = com(na, na)

   immediately after generating its challenge nonce na, and stores
   the resulting value in an implementation-defined audit log.  The
   audit tag is intended for offline reconciliation against
   external sources of evidence and is never transmitted.

   This document defines com as a binary function symbol whose
   semantics are deliberately left unconstrained; implementers MAY
   use any deterministic combiner that meets their auditing needs.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   H is a cryptographic hash function.  XOR denotes bitwise
   exclusive-or applied to equally sized octet strings.  com is a
   deterministic binary combiner whose specific construction is
   chosen by the implementation.  na is the initiator nonce, nb is
   the responder nonce, and k is the shared symmetric key.  The
   role names I and R denote the initiator and the responder.


3.  Protocol Overview

   CR-XOR-IAudit runs in a single round trip on the wire:

      Initiator                                       Responder
          |                                                |
          |                  na                            |
          |----------------------------------------------->|
          |                                                |
          |        H(na XOR k XOR nb), nb                  |
          |<-----------------------------------------------|
          |                                                |
          |  verify H tag                                  |
          |                                                |

   On the initiator side, immediately after generating na, the
   implementation also derives tag_audit_I = com(na, na) and stores
   it in an internal audit log.  The audit log is local to the
   initiator and is not exchanged with the responder.


4.  Message Format

      struct {
          opaque  challenge[L_n];
      } InitiatorFlight;

      struct {
          opaque  tag[L_h];
          opaque  response_nonce[L_n];
      } ResponderFlight;

   The audit tag has no wire encoding because it is never
   transmitted.  Implementations are free to encode it locally in
   whatever format the audit infrastructure expects.


5.  Processing Rules

   The shared key k MUST be established out of band.  k MUST be
   drawn uniformly at random and MUST be kept secret to both
   endpoints.

   An implementation in role I performs the following steps.

   1.  Generate a fresh nonce na of length L_n.  na MUST NOT be
       reused across runs.

   2.  Compute tag_audit_I = com(na, na) and append it to the
       initiator's audit log.  The audit step MUST NOT modify any
       protocol state used by step 3.

   3.  Transmit InitiatorFlight{ challenge = na } and retain na.

   4.  Wait for a ResponderFlight.  On receipt of <tag, nb>:

       a.  Verify that nb has length L_n and is non-zero.

       b.  Compute t' = H(na XOR k XOR nb).

       c.  Compare t' to tag in constant time.

       d.  If t' equals tag, declare the responder authenticated;
           otherwise abort.

   5.  Discard na after step 4.

   An implementation in role R, on receipt of an InitiatorFlight,
   MUST verify that na has length L_n and is non-zero, generate a
   fresh nb of length L_n, compute t = H(na XOR k XOR nb), and
   transmit <t, nb>.


6.  Security Considerations

   CR-XOR-IAudit is designed to convince the initiator that the
   holder of k has reacted to the current challenge.  When the
   verification at step 5.4.c succeeds, the initiator can conclude
   that the responder has been active at some point in time and is
   in possession of k.  This property is sometimes referred to as
   aliveness of the responder.

   The audit tag tag_audit_I is local to the initiator, never
   appears on the wire, and is not consumed by any protocol
   verification step.  The protocol's authentication guarantees do
   not depend on the construction of com.  An implementation MAY
   use a hash function, a fixed identity, or any other deterministic
   combiner; this document does not impose any such requirement.

   The hash function H provides the cryptographic barrier against
   forgery of the responder flight.  H MUST be selected so that the
   work factor of preimage and collision attacks exceeds the
   lifetime value of k.

   The non-zero check on the nonces removes a degenerate case in
   which an attacker submits the all-zeros nonce; without the
   check, the algebraic identity x XOR x = 0 could be exploited to
   drive the hash input into a state that is independent of one of
   the nonces.

   Implementers should be aware that the construction H(na XOR k
   XOR nb) is bilinear with respect to its operands.  An active
   attacker that observes one valid responder flight for a
   challenge na', and that is in a position to reroute traffic, can
   choose a fresh challenge na for an honest initiator and deliver
   a crafted response_nonce nb' = na XOR na' XOR nb together with
   the originally observed tag.  Under these circumstances the
   initiator's tag check succeeds even though the responder did not
   react to na.  CR-XOR-IAudit therefore does not provide agreement
   on the per-session parameters; it provides aliveness of the
   entity holding k, and nothing stronger.

   Implementations should also be aware that the audit tag stored
   in the local log can leak the value of na if the audit log is
   exposed to an adversary, depending on the construction of com.
   The audit log MUST be protected with at least the same
   confidentiality as na itself.

   Compromise of k breaks all guarantees of CR-XOR-IAudit, both for
   past and future runs.  Implementations SHOULD provide a
   mechanism to rotate k.

   na and nb appear in cleartext on the wire and MUST NOT carry
   implicit information about the endpoints.  Deployments operating
   over open networks SHOULD rate-limit incoming InitiatorFlights
   at a lower layer.
