              A Challenge-Response Authentication Protocol
                  with Initiator Challenge Retransmission
                       draft-famed-crxor-irtx-00


Abstract

   This document specifies CR-XOR-IRtx, a two-flow challenge-response
   authentication protocol between two endpoints that already share
   a long-term symmetric key.  To improve reachability over lossy
   forward links, the initiator transmits each challenge twice in
   immediate succession.  Both transmissions carry identical
   content; the responder reacts to the first copy that arrives and
   silently discards any subsequent identical copy that belongs to
   the same in-flight challenge.

1.  Introduction

   CR-XOR-IRtx provides a compact mechanism by which an initiator
   verifies that a peer holding a pre-shared key is reachable and
   currently active, while tolerating single-packet loss on the
   forward path.  After generating its challenge nonce, the
   initiator transmits the resulting flight twice in immediate
   succession.  The two transmissions carry identical content.  The
   responder's processing logic is invariant with respect to which
   transmission arrives first; later identical copies of the same
   challenge are ignored within the lifetime of a single in-flight
   challenge.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   H is a cryptographic hash function.  XOR denotes bitwise
   exclusive-or applied to equally sized octet strings.  na is the
   initiator nonce, nb is the responder nonce, and k is the shared
   symmetric key.  The role names I and R denote the initiator and
   the responder.


3.  Protocol Overview

   CR-XOR-IRtx runs in a single logical round trip:

      Initiator                                       Responder
          |                                                |
          |                  na                            |
          |----------------------------------------------->|
          |                  na                            |
          |----------------------------------------------->|
          |                                                |
          |        H(na XOR k XOR nb), nb                  |
          |<-----------------------------------------------|
          |                                                |
          |  verify H tag                                  |
          |                                                |

   The initiator generates a uniformly random nonce na of length
   L_n and transmits the challenge twice in immediate succession on
   the same outgoing path.  The responder, upon receipt of the
   first copy, generates a fresh nb of length L_n, computes t = H(na
   XOR k XOR nb), and transmits <t, nb>.  Any second copy of the
   same challenge that arrives during the same in-flight window is
   silently dropped.


4.  Message Format

      struct {
          opaque  challenge[L_n];
      } InitiatorFlight;

      struct {
          opaque  tag[L_h];
          opaque  response_nonce[L_n];
      } ResponderFlight;

   The two transmissions of the InitiatorFlight are byte-for-byte
   identical.  No sequence number, retransmission counter, or
   timestamp is added.


5.  Processing Rules

   The shared key k MUST be established out of band.  k MUST be
   drawn uniformly at random and MUST be kept secret to both
   endpoints.

   An implementation in role I performs the following steps.

   1.  Generate a fresh nonce na of length L_n.  na MUST NOT be
       reused across runs.

   2.  Transmit two identical copies of InitiatorFlight{ challenge
       = na } in immediate succession on the same outgoing path
       and retain na.

   3.  Wait for a ResponderFlight.  Upon receipt of <tag, nb>:

       a.  Verify that nb has length L_n and is non-zero.

       b.  Compute t' = H(na XOR k XOR nb).

       c.  Compare t' to tag in constant time.

       d.  If t' equals tag, declare the responder authenticated
           for the current run; otherwise abort.

   4.  Discard na after step 3.

   An implementation in role R MUST react to the first copy of
   each InitiatorFlight only.  Any subsequent flight whose
   challenge field is byte-for-byte identical to a challenge
   already accepted within the current in-flight window MUST be
   silently discarded.  On the first copy, the responder MUST
   verify that na has length L_n and is non-zero, generate a fresh
   nb of length L_n, compute t = H(na XOR k XOR nb), and transmit
   <t, nb>.


6.  Security Considerations

   CR-XOR-IRtx is designed to convince the initiator that the
   holder of k has reacted to the current challenge.  When the
   verification at step 5.3.c succeeds, the initiator can conclude
   that the responder has been active at some point in time and is
   in possession of k.  This property is sometimes referred to as
   aliveness of the responder.

   The duplicate transmission is intended only as a robustness
   mechanism for lossy forward paths and contributes nothing to
   the cryptographic guarantees.  Implementations that operate
   over reliable transports MAY transmit only a single copy of
   the InitiatorFlight without affecting the security analysis.

   The deduplication rule on the responder is necessary to
   prevent an honest responder from generating two distinct
   ResponderFlights in reply to a single logical challenge, which
   would consume entropy from the responder's random source for
   no benefit and would expose two valid tags computed under the
   same key material for the same na.

   The hash function H provides the cryptographic barrier against
   forgery of the responder flight.  H MUST be selected so that
   the work factor of preimage and collision attacks exceeds the
   lifetime value of k.

   The non-zero check on na removes a degenerate case in which an
   attacker submits the all-zeros nonce; without the check, the
   algebraic identity x XOR x = 0 could be exploited to drive the
   hash input into a state that is independent of one of the
   nonces.

   Implementers should be aware that the construction H(na XOR k
   XOR nb) is bilinear with respect to its operands.  An active
   attacker that observes one valid responder flight for a
   challenge na', and that is in a position to reroute traffic,
   can choose a fresh challenge na for an honest initiator and
   deliver a crafted response_nonce nb' = na XOR na' XOR nb
   together with the originally observed tag.  Under these
   circumstances the initiator's tag check succeeds even though
   the responder did not react to na.  CR-XOR-IRtx therefore does
   not provide agreement on the per-session parameters; it
   provides aliveness of the entity holding k, and nothing
   stronger.

   Compromise of k breaks all guarantees of CR-XOR-IRtx, both for
   past and for future runs.  Implementations SHOULD provide a
   mechanism to rotate k.

   na and nb appear in cleartext on the wire and MUST NOT carry
   implicit information about the endpoints.  Deployments operating
   over open networks SHOULD rate-limit incoming InitiatorFlights
   at a lower layer; the duplicate-transmission feature does not
   amplify denial-of-service surface beyond a constant factor.
