              A Challenge-Response Authentication Protocol
                  Using XOR-Combined Hash Verification
                          draft-famed-crxor-00


Abstract

   This document specifies CR-XOR, a lightweight two-flow
   challenge-response authentication protocol intended for
   point-to-point links between two endpoints that already share a
   long-term symmetric key.  The initiator issues a fresh nonce as a
   challenge, and the responder returns a fresh nonce together with a
   hash that binds the challenge, the responder nonce, and the shared
   key by means of bitwise exclusive-or.  CR-XOR uses a single hash
   primitive and produces compact wire formats, which makes it
   attractive for constrained devices that cannot afford a full
   keyed-MAC stack.

1.  Introduction

   Many constrained environments require a small protocol by which one
   endpoint can verify that a peer holding a pre-shared secret is
   reachable and currently active.  Full-fledged authentication
   protocols based on a keyed message authentication code or on a
   public-key signature are often too expensive for such links, both
   in code size and in transmitted octets.  CR-XOR addresses this gap
   with a fixed two-flow exchange, a single cryptographic hash
   primitive, and a wire format that carries only nonces and one hash
   value.

   The protocol is asymmetric: the initiator sends a challenge and
   then verifies the responder's reply, while the responder reacts to
   an incoming challenge without keeping per-session state across
   flights.  The initiator concludes that the responder is alive and
   in possession of the shared key when the verification check
   succeeds.

   This document defines the wire format, the processing rules, and
   the security properties that implementers can rely upon.  Section 6
   discusses the threat model in detail and is REQUIRED reading for
   any deployment.

2.2.  Notation

   The following notation is used throughout this document.

      H(x)        A cryptographic hash function applied to the octet
                  string x.  H is required to provide preimage and
                  collision resistance at the security level matching
                  k (Section 6).

      x XOR y     The bitwise exclusive-or of two equally sized octet
                  strings x and y.

      <a, b>      The concatenation of a and b in the order shown,
                  using the encoding given in Section 4.

      na, nb      The initiator nonce and the responder nonce,
                  respectively.

      k           The long-term symmetric key shared between the two
                  endpoints.

      I, R        The initiator role and the responder role.

   All XOR operations in this document operate on inputs of identical
   length L_n.  Implementations MUST reject any flight in which the
   nonces do not have length L_n.


3.  Protocol Overview

   CR-XOR consists of a single round trip between the initiator I and
   the responder R, executed once per authentication attempt:

      Initiator                                       Responder
          |                                                |
          |                  na                            |
          |----------------------------------------------->|
          |                                                |
          |        H(na XOR k XOR nb), nb                  |
          |<-----------------------------------------------|
          |                                                |
          |  verify H(na XOR k XOR nb) against received    |
          |                                                |

   The initiator generates a uniformly random nonce na of length L_n
   and transmits it to the responder.  Upon receipt, the responder
   generates its own random nonce nb of length L_n, computes the
   tag

         t = H(na XOR k XOR nb)

   and transmits the pair <t, nb>.  The initiator recomputes t' from
   the received nb together with its previously sent na and the
   shared key k, and compares t' to the received tag.

   A successful verification at the initiator constitutes the only
   security event produced by the protocol.  In particular, no
   confirmation message is sent back to the responder, and the
   responder does not learn whether the verification succeeded.


4.  Message Format

   Both flights are encoded as a sequence of fixed-length fields.  The
   length L_n MUST be agreed out of band and MUST be at least 16
   octets.  The hash output length L_h is fixed by the chosen hash
   function.

      struct {
          opaque  challenge[L_n];
      } InitiatorFlight;

      struct {
          opaque  tag[L_h];
          opaque  response_nonce[L_n];
      } ResponderFlight;

   The InitiatorFlight carries the challenge na.  The ResponderFlight
   carries the tag t and the responder nonce nb in this order.  No
   length prefixes, framing octets, or version markers are included
   on the wire.  Implementations that need framing MUST provide it at
   a lower layer.

   The relative ordering of fields within ResponderFlight is
   significant; reversing the order changes the verification input
   read by the initiator and is treated as a malformed flight.


5.  Processing Rules

5.1.  Key Setup

   Prior to the first protocol run, the two endpoints MUST establish a
   shared long-term key k of length L_k by an out-of-band channel.
   The provisioning of k is outside the scope of this document.  k
   MUST be drawn uniformly at random and MUST be kept secret to both
   endpoints.

   A given key k MAY be used for an unbounded number of CR-XOR runs;
   the protocol does not depend on a session counter or a key
   schedule beyond k itself.

5.2.  Initiator Processing

   To start an authentication attempt, an implementation acting in the
   role I performs the following steps.

   1.  Generate a fresh nonce na of length L_n using a cryptographically
       strong random source.  na MUST NOT be reused across runs.

   2.  Transmit InitiatorFlight{ challenge = na } to the responder
       and retain na in protocol state.

   3.  Wait for a ResponderFlight.  Upon receipt of <tag, nb>:

       a.  Verify that nb has length L_n.  If not, abort.

       b.  Verify that nb is non-zero.  Implementations MUST reject
           any flight in which nb is the all-zeros string of length
           L_n.

       c.  Compute t' = H(na XOR k XOR nb).

       d.  Compare t' to tag.  Comparison MUST be performed in
           constant time with respect to the input length.

       e.  If t' equals tag, declare the responder authenticated for
           the current run.  Otherwise abort and discard na.

   4.  In all cases, na MUST be discarded after step 3 so that no
       subsequent flight can re-use it.

5.3.  Responder Processing

   An implementation acting in the role R, on receipt of a flight
   that decodes as InitiatorFlight{ challenge = na }, performs the
   following steps.

   1.  Verify that na has length L_n.  If not, drop the flight.

   2.  Verify that na is non-zero.  Implementations MUST reject any
       flight in which na is the all-zeros string of length L_n.

   3.  Generate a fresh nonce nb of length L_n.  nb MUST NOT be
       reused across runs.

   4.  Compute t = H(na XOR k XOR nb).

   5.  Transmit ResponderFlight{ tag = t, response_nonce = nb }.

   The responder retains no state across flights and MAY process
   multiple incoming challenges concurrently.


6.  Security Considerations

   CR-XOR is designed to convince the initiator that the holder of k
   has reacted to the current challenge.  When the verification at
   step 3.e of Section 5.2 succeeds, the initiator can conclude that
   the responder has been active at some point in time and is in
   possession of k.  This property is sometimes referred to as
   aliveness of the responder.

   The hash function H provides the only barrier against forgery of
   the responder flight.  An attacker who can compute preimages of H
   under k can construct accepting flights without holding k, and an
   attacker who can find collisions in H can substitute one valid
   flight for another.  H MUST therefore be selected so that the
   work factor of preimage and collision attacks exceeds the lifetime
   value of k.

   The non-zero check at step 5.2.3.b and step 5.3.2 removes a
   trivial degenerate case in which an attacker submits the
   all-zeros nonce; without the check, an active attacker could
   exploit the algebraic identity x XOR x = 0 to drive the hash input
   into a state that is independent of one of the nonces.

   Implementers should be aware that the construction H(na XOR k XOR
   nb) is bilinear with respect to its operands.  An active attacker
   that observes one valid responder flight <t, nb> for a challenge
   na', and that is in a position to reroute traffic on the link, can
   choose a fresh challenge na for an honest initiator and deliver a
   crafted response_nonce nb' = na XOR na' XOR nb together with the
   originally observed t.  Under these circumstances the initiator's
   verification check at step 5.2.3 will succeed even though the
   responder has not reacted to na.  CR-XOR therefore does not
   provide agreement on the per-session parameters; it provides
   aliveness of the entity holding k, and nothing stronger.

   Deployments that need agreement on session parameters MUST
   compose CR-XOR with an additional layer that binds the verified
   exchange to specific session identifiers, for example by deriving
   a session key from t and using that key to protect subsequent
   traffic.  Such bindings are out of scope for this document.

   Compromise of k breaks all guarantees of CR-XOR, both for past and
   for future runs.  Implementations SHOULD provide a mechanism to
   rotate k, and SHOULD treat any indication of key compromise as a
   reason to invalidate all past authentications.

   CR-XOR does not protect the privacy of na or nb; both nonces
   appear in cleartext on the wire and MUST NOT carry implicit
   information about the endpoints.

   The protocol does not include any defense against denial-of-service
   amplification at the responder.  Deployments operating over open
   networks SHOULD rate-limit incoming InitiatorFlights at a lower
   layer.
