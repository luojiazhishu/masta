              A Challenge-Response Authentication Protocol
                       Without Tag Verification
                       draft-famed-crxor-novfy-00


Abstract

   This document specifies CR-XOR-NoVfy, a two-flow protocol between
   two endpoints that already share a long-term symmetric key.  The
   initiator generates a fresh challenge nonce and the responder
   returns a fresh nonce together with a hash tag computed over the
   exclusive-or combination of the nonces and the shared key.  The
   initiator accepts the responder's flight without performing any
   cryptographic check on the tag and treats the protocol as
   completed once the second flight has been received.

1.  Introduction

   CR-XOR-NoVfy is a deliberately minimal two-flight exchange in
   which the initiator transmits a challenge and the responder
   replies with a hash tag and a fresh nonce.  The protocol is
   intended for environments in which the second flight is treated
   as an acknowledgment that some peer has reacted to the
   challenge, and in which no cryptographic decision is taken on
   the basis of the tag.

   This document defines the wire format and the processing rules
   so that interoperable implementations can be produced.  The
   security properties available under this profile are spelled
   out in Section 6 in detail.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   H is a cryptographic hash function.  XOR denotes bitwise
   exclusive-or applied to equally sized octet strings.  na is the
   initiator nonce, nb is the responder nonce, and k is the shared
   symmetric key.  The role names I and R denote the initiator and
   the responder.


3.  Protocol Overview

   CR-XOR-NoVfy runs in a single round trip:

      Initiator                                       Responder
          |                                                |
          |                  na                            |
          |----------------------------------------------->|
          |                                                |
          |        H(na XOR k XOR nb), nb                  |
          |<-----------------------------------------------|
          |                                                |
          |  accept on receipt of any well-formed flight   |
          |                                                |

   The initiator generates a uniformly random nonce na of length
   L_n and transmits it.  Upon receipt the responder generates a
   fresh nonce nb of length L_n, computes the tag t = H(na XOR k
   XOR nb), and transmits the pair <t, nb>.  The initiator accepts
   the second flight as soon as it is parseable and concludes the
   run without inspecting t.


4.  Message Format

      struct {
          opaque  challenge[L_n];
      } InitiatorFlight;

      struct {
          opaque  tag[L_h];
          opaque  response_nonce[L_n];
      } ResponderFlight;

   The relative ordering of fields within ResponderFlight is
   significant for parsing only; reversing the order is treated as
   a malformed flight.


5.  Processing Rules

   The shared key k MUST be established out of band.  k MUST be
   drawn uniformly at random and MUST be kept secret to both
   endpoints.

   An implementation in role I performs the following steps.

   1.  Generate a fresh nonce na of length L_n.  na MUST NOT be
       reused across runs.

   2.  Transmit InitiatorFlight{ challenge = na } and retain na.

   3.  Wait for a ResponderFlight.  On receipt of any well-formed
       <tag, nb>:

       a.  Verify that nb has length L_n and is non-zero.

       b.  Conclude the run.

   4.  Discard na after step 3.

   An implementation in role R, on receipt of an InitiatorFlight,
   MUST verify that na has length L_n and is non-zero, generate a
   fresh nb of length L_n, compute t = H(na XOR k XOR nb), and
   transmit ResponderFlight{ tag = t, response_nonce = nb }.


6.  Security Considerations

   CR-XOR-NoVfy provides essentially no cryptographic guarantees
   to the initiator.  Although the responder computes a hash tag
   over the shared key and the two nonces, the initiator does not
   inspect the tag and accepts any well-formed second flight.  An
   active attacker that is in a position to inject traffic on the
   return path can therefore fabricate a tag and a response nonce
   without holding k and without having any honest responder
   participate in the run.

   Specifically, this protocol does not provide aliveness of the
   responder.  The initiator can complete a run successfully even
   when no entity in possession of k has reacted to the challenge,
   so a successful run cannot be used as evidence that the peer is
   present, reachable, or in possession of k.  Implementations
   MUST NOT consume the outcome of CR-XOR-NoVfy as an
   authentication signal.

   Implementations MUST NOT compose CR-XOR-NoVfy with any layer
   that requires authentication of the responder, key
   confirmation, or fresh participation by the responder.  The
   protocol is suitable only for transport-layer reachability
   measurements that explicitly tolerate forged returns.

   The hash function H continues to be evaluated by the responder
   for compatibility with downstream consumers that may inspect
   the tag out of band.  H MUST be selected so that the work
   factor of preimage and collision attacks exceeds the lifetime
   value of k, in case such out-of-band consumers exist.

   The non-zero check on the nonces removes a degenerate parsing
   case but does not contribute to authentication.

   Compromise of k breaks any out-of-band use of the tag.
   Implementations SHOULD provide a mechanism to rotate k.

   na and nb appear in cleartext on the wire and MUST NOT carry
   implicit information about the endpoints.  Deployments
   operating over open networks SHOULD rate-limit incoming
   InitiatorFlights at a lower layer.
