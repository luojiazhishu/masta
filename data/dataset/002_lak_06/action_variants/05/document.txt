      Lightweight Authentication Protocol for Low-Cost RFID Systems
                          draft-famed-lak06-00


Abstract

   This document specifies a lightweight challenge-response
   authentication protocol intended for Radio Frequency
   Identification (RFID) deployments in which a Reader and a Tag
   share a long-term symmetric key prior to deployment.  The
   protocol exchanges three messages over the air interface and
   relies exclusively on a one-way hash function and the bitwise
   exclusive-OR operator.  The Tag response is prefixed with a
   fixed framing label so that the Reader can demultiplex
   incoming responses without having to parse a length field.
   This memo describes the message format, the processing
   rules, and the security properties of the resulting
   exchange.

1.  Introduction

   Radio Frequency Identification (RFID) systems are widely
   deployed in inventory management, access control, and
   anti-counterfeiting applications.  Passive Tags draw their
   operating energy from the interrogating field, which forces
   the Tag side to use a very small set of primitives.

   This document specifies a three-message authentication
   protocol that establishes a mutually authenticated session
   between a Reader and a Tag, on the basis of a long-term
   symmetric key shared between the two parties.  The Tag
   response carries a fixed framing label "TAG_HDR" ahead of
   r1 and the Tag's MAC, so that Reader implementations can
   identify response frames without further parsing logic.

2.2.  Symbols

   The following symbols are used throughout the document.

      Reader   The interrogator.

      Tag      The passive transponder.

      k        A long-term symmetric key shared between a
               specific Reader and a specific Tag.

      r0       A nonce drawn by the Reader for the current
               session.

      r1       A nonce drawn by the Tag for the current
               session.

      'TAG_HDR' A fixed framing label that prefixes the Tag
               response.

      h(x)     A one-way, preimage- and second-preimage-
               resistant hash function.

      a XOR b  Bitwise exclusive-OR of equal-length bit
               strings.

      a, b     Concatenation on the wire.


3.  Protocol Overview

   A single run of the protocol involves three messages
   exchanged between one Reader and one Tag, in the order R0,
   T1, R1.

      Reader                                            Tag
        |                                                |
        |  R0:  r0                                       |
        |----------------------------------------------->|
        |                                                |
        |  T1:  'TAG_HDR', r1, h(r0 XOR r1 XOR k)        |
        |<-----------------------------------------------|
        |                                                |
        |  R1:  h(h(r0 XOR r1 XOR k) XOR k XOR r0)       |
        |----------------------------------------------->|
        |                                                |

   r0 and r1 are fresh per session and MUST NOT be reused.


4.  Message Format

4.1.  Reader Challenge (R0)

      struct {
          opaque r0[NonceLen];
      } ReaderChallenge;

4.2.  Tag Response (T1)

      struct {
          opaque label[7];     /* "TAG_HDR" */
          opaque r1[NonceLen];
          opaque tag_mac[HashLen];
      } TagResponse;

   label MUST be the seven-byte ASCII constant "TAG_HDR".
   tag_mac = h(r0 XOR r1 XOR k), where r0 is the value
   received in the preceding R0 message.

4.3.  Reader Confirmation (R1)

      struct {
          opaque reader_mac[HashLen];
      } ReaderConfirmation;

   reader_mac = h(tag_mac XOR k XOR r0).


5.  Processing Rules

5.1.  Provisioning

   Each Reader-Tag pair MUST be configured with a shared
   long-term key k before its first interrogation.

5.2.  Reader Procedure

      1.  Draw a fresh r0 from a cryptographically strong
          random source [RFC4086]; transmit R0.

      2.  Wait for T1.  Read the framing label; if it differs
          from 'TAG_HDR', the Reader MUST silently discard the
          message.

      3.  Read r1 and tag_mac from T1.

      4.  Compute expected = h(r0 XOR r1 XOR k); compare with
          tag_mac.  If the comparison fails, abort and MUST
          NOT emit R1.

      5.  Compute reader_mac = h(tag_mac XOR k XOR r0);
          transmit R1.

5.3.  Tag Procedure

      1.  Read r0 from R0.

      2.  Draw a fresh r1.

      3.  Compute tag_mac = h(r0 XOR r1 XOR k); transmit T1
          carrying ('TAG_HDR', r1, tag_mac).

      4.  Wait for R1 carrying reader_mac.

      5.  Compute expected = h(tag_mac XOR k XOR r0);
          compare with reader_mac.  If the comparison fails,
          the Tag MUST silently discard R1.


6.  Security Considerations

   The protocol relies on the confidentiality of k and on the
   one-way and second-preimage resistance of h.

   Confidentiality of k.  Implementations MUST protect k both
   at rest and during provisioning.

   Authentication of the Reader by the Tag.  When the Tag
   accepts R1, reader_mac binds the same triple (r0, r1, k)
   that the Tag itself contributed to.

   Limitation on the Reader's view of the Tag.  This protocol
   does not guarantee that, when the Reader accepts T1, the
   pair (r0, r1) recorded by the Reader is the same pair that
   the responding holder of k actually computed against.  An
   attacker on the air interface MAY exploit the linearity of
   the exclusive-OR construction to inject an offset Delta
   into r0 and remove the same offset from r1 in such a
   manner that the Reader's check of tag_mac still succeeds.
   Implementations that require an injective binding SHOULD
   layer an additional confirmation on top of this protocol.

   Status of the framing label.  The 'TAG_HDR' label is a
   transport-level marker, not a security input.  An attacker
   MAY rewrite the label to cause the Reader to discard a
   message, but cannot leverage the label itself to forge a
   MAC.  Implementations MUST NOT fold the label into the
   MAC inputs.

   Replay across sessions.  Implementations MUST draw r0 and
   r1 from a source whose collision probability over the
   lifetime of k is negligible [RFC4086].

   Long-term key compromise.  Forward security with respect to
   long-term key compromise is not provided.
