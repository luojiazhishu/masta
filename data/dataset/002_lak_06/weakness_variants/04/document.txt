      Lightweight Authentication Protocol for Low-Cost RFID Systems
                          draft-famed-lak06-00


Abstract

   This document specifies a lightweight challenge-response
   authentication protocol intended for Radio Frequency
   Identification (RFID) deployments in which a Reader and a Tag
   share a long-term symmetric key prior to deployment.  The
   protocol exchanges three messages over the air interface and
   relies exclusively on a one-way hash function and the bitwise
   exclusive-OR operator.  In this profile the Reader's
   confirmation MAC mixes the Tag's authenticated response and
   the Reader's own challenge, without re-binding the long-term
   key.  This memo describes the message format, the
   processing rules, and the security properties of the
   resulting exchange.

1.  Introduction

   Radio Frequency Identification (RFID) systems are widely
   deployed in inventory management, access control, and
   anti-counterfeiting applications.

   This document specifies a three-message authentication
   protocol that establishes a session between a Reader and a
   Tag on the basis of a long-term symmetric key shared between
   the two parties.  The Reader's confirmation MAC binds the
   Tag's MAC and the Reader's own challenge, without
   re-binding the long-term key.

2.2.  Symbols

   The following symbols are used throughout the document.

      Reader   The interrogator.

      Tag      The passive transponder.

      k        A long-term symmetric key shared between a
               specific Reader and a specific Tag.

      r0       A nonce drawn by the Reader for the current
               session.

      r1       A nonce drawn by the Tag for the current
               session.

      h(x)     A one-way, preimage- and second-preimage-
               resistant hash function.

      a XOR b  Bitwise exclusive-OR of equal-length bit
               strings.

      a, b     Concatenation on the wire.


3.  Protocol Overview

   A single run of the protocol involves three messages
   exchanged between one Reader and one Tag, in the order R0,
   T1, R1.

      Reader                                            Tag
        |                                                |
        |  R0:  r0                                       |
        |----------------------------------------------->|
        |                                                |
        |  T1:  r1, h(r0 XOR r1 XOR k)                   |
        |<-----------------------------------------------|
        |                                                |
        |  R1:  h(h(r0 XOR r1 XOR k) XOR r0)             |
        |----------------------------------------------->|
        |                                                |

   r0 and r1 are fresh per session and MUST NOT be reused.


4.  Message Format

4.1.  Reader Challenge (R0)

      struct {
          opaque r0[NonceLen];
      } ReaderChallenge;

4.2.  Tag Response (T1)

      struct {
          opaque r1[NonceLen];
          opaque tag_mac[HashLen];
      } TagResponse;

   tag_mac = h(r0 XOR r1 XOR k).

4.3.  Reader Confirmation (R1)

      struct {
          opaque reader_mac[HashLen];
      } ReaderConfirmation;

   reader_mac = h(tag_mac XOR r0).


5.  Processing Rules

5.1.  Provisioning

   Each Reader-Tag pair MUST be configured with a shared
   long-term key k before its first interrogation.

5.2.  Reader Procedure

      1.  Draw a fresh r0 from a cryptographically strong
          random source [RFC4086]; transmit R0.

      2.  Wait for T1 carrying (r1, tag_mac).

      3.  Compute expected = h(r0 XOR r1 XOR k); compare with
          tag_mac.  If the comparison fails, abort and MUST
          NOT emit R1.

      4.  Compute reader_mac = h(tag_mac XOR r0); transmit
          R1.

5.3.  Tag Procedure

      1.  Read r0 from R0.

      2.  Draw a fresh r1.

      3.  Compute tag_mac = h(r0 XOR r1 XOR k); transmit T1.

      4.  Wait for R1 carrying reader_mac.

      5.  Compute expected = h(tag_mac XOR r0); compare with
          reader_mac.  If the comparison fails, the Tag MUST
          silently discard R1.


6.  Security Considerations

   The protocol relies on the confidentiality of k for the
   first hash, and on the one-way and second-preimage
   resistance of h.

   Confidentiality of k.  Implementations MUST protect k both
   at rest and during provisioning.

   This protocol does not provide entity authentication of
   the Reader by the Tag.  Because reader_mac is computed
   over tag_mac and r0 only, no secret material is required
   to forge it: an attacker on the air interface that
   observes T1 can recompute reader_mac independently of k
   and replay it to the Tag.  The Tag's check
   h(tag_mac XOR r0) will succeed even when no holder of
   k participated in producing R1, so the Tag will commit
   to the session against the attacker's chosen r0.

   Implementations should be aware that the Reader's
   confirmation step in this profile carries no proof of
   knowledge of k; the only authenticated message in the
   exchange is T1.  Deployments that need mutual
   authentication MUST use a profile in which the Reader's
   confirmation MAC is keyed by k.

   This protocol also does not protect against the
   exclusive-OR offset attack on the Reader side that is
   already inherent to the exchange when k is used to key
   tag_mac.

   Replay across sessions.  Implementations MUST draw r0 and
   r1 from a source whose collision probability over the
   lifetime of k is negligible [RFC4086].

   Long-term key compromise.  Forward security with respect to
   long-term key compromise is not provided.
