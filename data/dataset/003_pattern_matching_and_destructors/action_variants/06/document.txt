    A Symmetric-Key Encapsulation Profile with Repeated Initiator Output
                  draft-famed-sk-pmd-v06-00


Abstract

   This document specifies a one-message symmetric-key encapsulation
   profile in which the initiator transmits the ciphertext twice.
   Both transmissions carry identical contents.  The responder
   processes the first valid instance and treats the second as a
   duplicate.

1.  Introduction

   This profile follows the structure of the base symmetric-key
   encapsulation.  Implementations of this profile transmit the
   single ciphertext message twice, in order to improve robustness
   against single-packet loss on the path between the initiator
   and the responder.

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL

3.  Protocol Overview

      Initiator (I)                                       Responder (R)
         |                                                     |
         |   1a.  msg                                          |
         |---------------------------------------------------->|
         |   1b.  msg                                          |
         |---------------------------------------------------->|
         |                          (release of pub to network)|

   where msg = senc(<sec, pub>, k).

4.  Message Format

   The on-wire ciphertext is the same fixed-format value

      msg = senc(<sec, pub>, k)

   transmitted twice.  Both transmissions MUST carry identical
   contents.

5.  Processing Rules

   The initiator emits msg twice with identical contents and a
   single set of locally drawn nonces (sec, pub).  The responder
   SHOULD process the first valid instance and SHOULD silently
   drop the second; the latter does not advance the responder's
   state.

6.  Security Considerations

   Duplicating msg does not introduce additional secret material
   and does not change the secrecy properties of the
   encapsulation.  An adversary that receives both copies of msg
   has no advantage over an adversary that observes only one.
   Implementations SHOULD ensure that processing the second copy
   never causes a second release of pub or any other duplicated
   side effect.
