    Public-Key Session Key Transport with Client Correlation Nonce
                       draft-famed-bsktcn-00

Abstract

   This document specifies a public-key session key transport protocol
   in which a client conveys a freshly generated session key to a
   server using the server's long-term public key, and the server
   confirms successful receipt by returning a one-way hash of the
   transported key alongside a client-supplied correlation nonce.  The
   correlation nonce is generated by the client at the same time as
   the session key, transmitted in the clear together with the
   encrypted key, and reflected unmodified by the server in its
   confirmation message.  This document defines the message exchange,
   processing rules, and the security properties on which conforming
   implementations may rely.

1. Introduction

   This document defines a minimal public-key session key transport
   exchange that is suitable for environments in which a client may
   issue several requests in parallel to the same server and needs to
   match each confirmation message to the corresponding outstanding
   request without inspecting the cryptographic payload.

   The client generates a fresh symmetric session key together with a
   fresh correlation nonce.  The session key is encrypted under the
   server's long-term public key; the correlation nonce is
   transmitted in the clear in the same message.  The server
   decrypts the encrypted key, computes a one-way hash of the
   recovered key, and returns the hash together with the original
   correlation nonce.  The client uses the returned correlation
   nonce to identify the outstanding request and the returned hash
   to confirm that the server has received the corresponding session
   key.

2.2. Notation

      C            The client; the party that initiates the exchange
                   and selects the session key.

      S            The server; the party that owns a long-term public
                   key pair.

      sk(S), pk(S) The long-term private and public key of S.

      k            The session key, fresh and uniformly random, drawn
                   by C for use in a single run of the protocol.

      rc           The client correlation nonce, fresh and uniformly
                   random, drawn by C for the same single run.

      aenc, adec   The asymmetric encryption and decryption functions
                   of the underlying public-key scheme.

      h(x)         A one-way hash function applied to x.

      <a, b>       The ordered concatenation of a and b in a single
                   message.

3. Protocol Overview

   The protocol consists of two messages exchanged between C and S.
   C is assumed to have obtained an authentic copy of pk(S) prior
   to the exchange.

         Client                                       Server
         ------                                       ------
         k  = fresh random
         rc = fresh random
         m1 = <aenc(k, pk(S)), rc>
                          ----- m1 ----->
                                                k = adec(.,sk(S))
                                                m2 = <h(k), rc>
                          <---- m2 ------
         locate request by rc
         verify m2.hash == h(k)

   On successful completion both parties hold the same session key
   k and the client has unambiguously associated the confirmation
   with its own outstanding request through rc.

4. Message Format

   The KeyTransport message m1 carries the asymmetric encryption of
   the session key followed by the client correlation nonce.

      struct {
          opaque ciphertext<1..2^16-1>;
          opaque correlation_nonce<8..32>;
      } KeyTransport;

   The KeyConfirm message m2 carries the one-way hash of the
   session key followed by the correlation nonce as received in
   the corresponding KeyTransport message.

      struct {
          opaque digest<1..2^8-1>;
          opaque correlation_nonce<8..32>;
      } KeyConfirm;

   The length of correlation_nonce is fixed at the granularity of a
   single deployment and SHOULD provide at least 64 bits of entropy.

5. Processing Rules

   On initiation, C generates k and rc as independent uniformly
   random values.  C then computes ciphertext = aenc(k, pk(S)),
   constructs m1, transmits m1 to S, and retains the pair (rc, k)
   in a table of outstanding requests.

   On receipt of m1, S computes k' = adec(ciphertext, sk(S)).  If
   decryption fails or yields a value that does not conform to the
   expected key format, S MUST discard m1 and abort the run.
   Otherwise S computes digest = h(k'), constructs m2 with the
   correlation_nonce field set to the value as received, and
   transmits m2 to C.

   On receipt of m2, C looks up the entry indexed by m2.
   correlation_nonce.  If no such entry exists, C MUST discard m2.
   Otherwise C computes h(k) for the retained k and compares it for
   equality with m2.digest.  If the values match, C MAY consider k
   to be accepted by S; otherwise C MUST discard k and abort the
   run.

6. Security Considerations

   Confidentiality of the session key relies on the IND-CCA security
   of the underlying asymmetric scheme and on the preimage
   resistance of h.  An adversary that does not hold sk(S) is
   unable to recover k from observed protocol traffic.  The
   correlation nonce rc is not secret; it is transmitted in the
   clear and serves no confidentiality purpose.

   The correlation nonce does not contribute to authentication.
   Server authentication is established by the fact that no party
   other than the holder of sk(S) is able to compute h(k) without
   first recovering k.  Replay of a previously observed
   KeyTransport message causes S to recompute the same digest and
   to reflect the same correlation nonce; because k is fresh in
   every run, a replay cannot cause C to accept a session key it
   did not itself generate.  An adversary that injects a fabricated
   m2 carrying an arbitrary digest and a known correlation nonce is
   detected by the digest comparison at C.

   The protocol does not provide forward secrecy with respect to
   compromise of sk(S); an adversary that obtains sk(S) is able to
   recover every session key transported under pk(S) over the
   lifetime of the key pair.  Implementations that require forward
   secrecy SHOULD compose this protocol with an ephemeral key
   agreement step.

   Implementations should be aware that rc is observable on the
   network and SHOULD NOT be reused across runs even when the
   underlying transport is reliable.
