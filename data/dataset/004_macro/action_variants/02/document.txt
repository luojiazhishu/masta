    Public-Key Session Key Transport with Server Response Nonce
                       draft-famed-bsktsn-00

Abstract

   This document specifies a public-key session key transport
   protocol in which a client conveys a freshly generated session
   key to a server using the server's long-term public key, and the
   server confirms successful receipt by returning a one-way hash
   of the transported key alongside a server-generated response
   nonce.  The response nonce is drawn freshly by the server in
   every run and serves to distinguish individual confirmation
   messages from one another at the application layer.

1. Introduction

   This document defines a minimal public-key session key transport
   exchange in which the client unilaterally selects a fresh session
   key and the server echoes a one-way hash of the recovered key
   together with a fresh server response nonce.  The server response
   nonce is generated by the server independently of the request and
   is intended to be carried opaquely by the client into any
   subsequent application-layer interaction in which the server
   wishes to attach a per-run identifier to its response.

   The protocol is deliberately small.  No message-specific
   identifiers, timestamps, or sequence numbers are negotiated by the
   protocol itself.  Implementations that require richer guarantees,
   such as mutual authentication or forward secrecy, are expected to
   compose this protocol with additional mechanisms.

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   The following notation is used throughout this document.

      C            The client.
      S            The server.
      sk(S), pk(S) The long-term private and public key of S.
      k            A fresh, uniformly random session key drawn by C.
      rs           A fresh, uniformly random response nonce drawn by
                   S.
      aenc, adec   Asymmetric encryption and decryption.
      h(x)         A one-way hash function.
      <a, b>       The ordered concatenation of a and b.

3. Protocol Overview

   The protocol consists of two messages exchanged between C and S.

         Client                                       Server
         ------                                       ------
         k  = fresh random
         m1 = aenc(k, pk(S))
                          ----- m1 ----->
                                                k  = adec(., sk(S))
                                                rs = fresh random
                                                m2 = <h(k), rs>
                          <---- m2 ------
         verify m2.hash == h(k)

   On successful completion C holds k as the session key and rs as
   an opaque response identifier supplied by S.  The interpretation
   of rs is left to the calling application.

4. Message Format

   The KeyTransport message m1 carries the asymmetric encryption of
   the session key.

      struct {
          opaque ciphertext<1..2^16-1>;
      } KeyTransport;

   The KeyConfirm message m2 carries the one-way hash of the
   session key followed by the server-generated response nonce.

      struct {
          opaque digest<1..2^8-1>;
          opaque response_nonce<8..32>;
      } KeyConfirm;

   The length of response_nonce is fixed at the granularity of a
   single deployment and SHOULD provide at least 64 bits of entropy.

5. Processing Rules

   On initiation, C generates k uniformly at random, computes
   ciphertext = aenc(k, pk(S)), transmits the resulting m1 to S, and
   retains k locally pending receipt of the corresponding
   KeyConfirm message.

   On receipt of m1, S computes k' = adec(ciphertext, sk(S)).  If
   decryption fails or yields a value that does not conform to the
   expected key format, S MUST discard m1 and abort the run.
   Otherwise S draws rs uniformly at random, computes
   digest = h(k'), constructs m2 with response_nonce set to rs, and
   transmits m2 to C.  S MAY retain rs for use in subsequent
   application-layer interactions.

   On receipt of m2, C computes h(k) for the retained k and
   compares it for equality with m2.digest.  If the values match,
   C MAY consider k to be accepted by S and MAY use rs as an
   opaque per-run identifier in subsequent interactions with S.
   Otherwise C MUST discard k and abort the run.

6. Security Considerations

   Confidentiality of the session key against a network adversary
   that does not hold sk(S) follows from the IND-CCA security of
   the underlying asymmetric scheme and the preimage resistance of
   h.  The response nonce rs is not secret; it is transmitted in
   the clear and contributes nothing to confidentiality.

   Receipt of a well-formed KeyConfirm message demonstrates to C
   that the holder of sk(S) has decrypted the corresponding
   KeyTransport ciphertext and computed h of the recovered key.
   The protocol authenticates S unilaterally and does not
   authenticate C.

   Replay of a previously observed KeyTransport message causes S
   to derive the same k' as on the original run, but rs is drawn
   freshly and so the replayed run produces a distinguishable
   KeyConfirm message at the application layer.  The freshness of
   k chosen by C in every run prevents the replay from causing C
   to accept a session key it did not itself generate.

   The protocol does not provide forward secrecy with respect to
   compromise of sk(S).  Implementations that require forward
   secrecy SHOULD compose this protocol with an ephemeral key
   agreement step.

   Implementations should be aware that rs is observable on the
   network and that any application-layer state indexed by rs is
   therefore visible to the adversary by inspection of network
   traffic.
