      Public-Key Session Key Transport with Acknowledgement Tag
                       draft-famed-bsktack-00

Abstract

   This document specifies a public-key session key transport
   protocol in which a client conveys a freshly generated session
   key to a server using the server's long-term public key, and the
   server confirms successful receipt by returning a one-way hash of
   the transported key prefixed by the fixed acknowledgement tag
   "ack".  The acknowledgement tag allows client-side dispatch logic
   to distinguish session-key confirmation messages from other
   server responses that may share the same listening socket.

1. Introduction

   This document defines a minimal public-key session key transport
   exchange that is suitable for environments in which the client
   may receive several distinct response types over a single
   transport endpoint and needs a coarse, in-the-clear discriminator
   to route incoming messages to the correct handler.

   The client generates a fresh symmetric session key, encrypts it
   under the server's long-term public key, and transmits the
   resulting ciphertext to the server.  The server decrypts the
   ciphertext, computes a one-way hash of the recovered key, and
   returns the hash together with a fixed acknowledgement tag with
   the value "ack".  The client uses the tag to dispatch the message
   and the hash to confirm that the server has received the
   corresponding session key.

2. Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   The following notation is used throughout this document.

      C, S         The client and the server.
      sk(S), pk(S) The long-term private and public key of S.
      k            A fresh, uniformly random session key drawn by C.
      aenc, adec   Asymmetric encryption and decryption.
      h(x)         A one-way hash function.
      "ack"        The fixed octet string identifying a session-key
                   confirmation message at the dispatch layer.
      <a, b>       The ordered concatenation of a and b.

3. Protocol Overview

         Client                                       Server
         ------                                       ------
         k  = fresh random
         m1 = aenc(k, pk(S))
                          ----- m1 ----->
                                                k  = adec(.,sk(S))
                                                m2 = <h(k), "ack">
                          <---- m2 ------
         check m2.tag == "ack"
         verify m2.digest == h(k)

   On successful completion both parties hold the same session key
   k.  The "ack" tag is fixed for all runs of the protocol and
   carries no per-run state.

4. Message Format

   The KeyTransport message m1 carries the asymmetric encryption of
   the session key.

      struct {
          opaque ciphertext<1..2^16-1>;
      } KeyTransport;

   The KeyConfirm message m2 carries the one-way hash of the
   recovered session key followed by the fixed acknowledgement tag.

      struct {
          opaque digest<1..2^8-1>;
          opaque tag[3];                  /* the three octets "ack" */
      } KeyConfirm;

   The value of the tag field is fixed for the protocol defined by
   this document and MUST be the three-octet ASCII string "ack".

5. Processing Rules

   On initiation, C generates k uniformly at random, computes
   ciphertext = aenc(k, pk(S)), constructs m1, and transmits m1 to
   S.  C retains k locally pending receipt of the corresponding
   KeyConfirm message.

   On receipt of m1, S computes k' = adec(ciphertext, sk(S)).  If
   decryption fails or yields a value that does not conform to the
   expected key format, S MUST discard m1 and abort the run.
   Otherwise S computes digest = h(k'), constructs m2 with tag set
   to "ack", and transmits m2 to C.

   On receipt of a candidate m2, C inspects the tag field.  If the
   tag does not equal "ack", C MUST defer dispatch to a handler
   defined elsewhere or, if no such handler is defined, MUST
   discard m2 and abort the run.  Otherwise C computes h(k) for
   the retained k and compares it for equality with m2.digest.
   If the values match, C MAY consider k to be accepted by S;
   otherwise C MUST discard k and abort the run.

6. Security Considerations

   Confidentiality of the session key against a network adversary
   that does not hold sk(S) follows from the IND-CCA security of
   the underlying asymmetric scheme and the preimage resistance of
   h.  The "ack" tag is public and contributes nothing to
   confidentiality; an adversary observing m2 learns only that the
   message is intended for the session-key confirmation handler.

   Server authentication is established by the fact that no party
   other than the holder of sk(S) is able to compute h(k) without
   first recovering k.  The protocol does not authenticate C, and
   the tag does not contribute to authentication.

   Replay of a previously observed KeyTransport message causes S
   to recompute the same digest; because k is fresh in every run,
   a replay cannot cause C to accept a session key it did not
   itself generate.  An adversary that flips the tag in a forged
   m2 to a value other than "ack" causes C to discard the message;
   such an adversary cannot induce C to accept a fabricated digest
   on the basis of the tag alone.

   The protocol does not provide forward secrecy with respect to
   compromise of sk(S).  Implementations that require forward
   secrecy SHOULD compose this protocol with an ephemeral key
   agreement step.

   Implementations should be aware that the acknowledgement tag
   exposes the message type to traffic analysis.  Operators that
   consider message-type confidentiality material SHOULD run this
   protocol over a transport that itself conceals the protocol
   identifier.
