   Public-Key Session Key Transport with Domain-Separated Hash
                       draft-famed-bsktdsh-00

Abstract

   This document specifies a public-key session key transport
   protocol in which a client conveys a freshly generated session
   key to a server using the server's long-term public key, and the
   server confirms successful receipt by returning a domain-
   separated one-way hash of the transported key.  The hash input
   is the concatenation of the recovered session key and a fixed
   domain-separation label "session", chosen so that the
   confirmation digest cannot be confused with one-way images of
   the same key produced for any other purpose.

1. Introduction

   This document defines a minimal public-key session key transport
   exchange in which the server confirmation hash is computed over
   the session key concatenated with a fixed domain-separation
   label.  Use of a domain-separated hash ensures that the digest
   produced by the protocol cannot be reinterpreted as a one-way
   image of the same key produced for an unrelated purpose, even
   when the same hash function is shared across protocols in the
   same deployment.

   The client generates a fresh symmetric session key, encrypts it
   under the server's long-term public key, and transmits the
   resulting ciphertext.  The server decrypts the ciphertext and
   returns h(<k, "session">) as confirmation.  The client recomputes
   h(<k, "session">) for its own k and compares the two values.

2. Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   The following notation is used throughout this document.

      C, S         The client and the server.
      sk(S), pk(S) The long-term private and public key of S.
      k            A fresh, uniformly random session key drawn by C.
      aenc, adec   Asymmetric encryption and decryption.
      h(x)         A one-way hash function applied to the encoding
                   of x.
      "session"    The fixed domain-separation label for the
                   confirmation digest.
      <a, b>       The ordered concatenation of a and b under a
                   canonical encoding.

3. Protocol Overview

         Client                                       Server
         ------                                       ------
         k  = fresh random
         m1 = aenc(k, pk(S))
                          ----- m1 ----->
                                                k  = adec(.,sk(S))
                                                m2 = h(<k, "session">)
                          <---- m2 ------
         verify m2 == h(<k, "session">)

   On successful completion both parties hold the same session key
   k.  The label "session" is fixed for the protocol defined by
   this document.

4. Message Format

   The KeyTransport message m1 carries the asymmetric encryption of
   the session key.

      struct {
          opaque ciphertext<1..2^16-1>;
      } KeyTransport;

   The KeyConfirm message m2 carries the domain-separated one-way
   hash of the recovered session key.

      struct {
          opaque digest<1..2^8-1>;
      } KeyConfirm;

   The digest field is computed as h(encode(<k, "session">)) where
   encode is a deterministic concatenation function fixed at the
   granularity of a single deployment and h is the negotiated hash
   function.

5. Processing Rules

   On initiation, C generates k uniformly at random, computes
   ciphertext = aenc(k, pk(S)), constructs m1, and transmits m1 to
   S.  C retains k locally pending receipt of the corresponding
   KeyConfirm message.

   On receipt of m1, S computes k' = adec(ciphertext, sk(S)).  If
   decryption fails or yields a value that does not conform to the
   expected key format, S MUST discard m1 and abort the run.
   Otherwise S computes digest = h(<k', "session">), constructs m2,
   and transmits m2 to C.

   On receipt of m2, C computes h(<k, "session">) for the retained
   k and compares it for equality with m2.digest.  If the values
   match, C MAY consider k to be accepted by S; otherwise C MUST
   discard k and abort the run.

6. Security Considerations

   Confidentiality of the session key against a network adversary
   that does not hold sk(S) follows from the IND-CCA security of
   the underlying asymmetric scheme and the preimage resistance of
   h.  The label "session" is public and contributes nothing to
   confidentiality.

   Server authentication is established by the fact that no party
   other than the holder of sk(S) is able to compute
   h(<k, "session">) without first recovering k.  The protocol does
   not authenticate C.

   The domain-separation label "session" prevents the confirmation
   digest from being confused with one-way images of the same key
   produced for any other purpose, including future protocols that
   might be deployed alongside this one and that might choose to
   compute h on the same key with a different label.  An adversary
   that obtains a valid digest h(<k, "session">) for some session
   key k cannot replay the digest as a confirmation for any other
   protocol that uses h with a different label or that does not
   apply domain separation.

   Replay of a previously observed KeyTransport message causes S
   to recompute the same digest; because k is fresh in every run,
   a replay cannot cause C to accept a session key it did not
   itself generate.

   The protocol does not provide forward secrecy with respect to
   compromise of sk(S).  Implementations that require forward
   secrecy SHOULD compose this protocol with an ephemeral key
   agreement step.
