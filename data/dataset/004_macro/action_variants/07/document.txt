  Public-Key Session Key Transport with Server-Bound Confirm Hash
                       draft-famed-bsktsb-00

Abstract

   This document specifies a public-key session key transport
   protocol in which a client conveys a freshly generated session
   key to a server using the server's long-term public key, and the
   server confirms successful receipt by returning a one-way hash
   computed over the recovered session key bound to the server's
   own identifier.  Inclusion of the server identifier in the
   hash input ensures that the confirmation digest is meaningful
   only with respect to a specific server identity and cannot be
   transposed across servers that share the same hash function.

1. Introduction

   This document defines a minimal public-key session key transport
   exchange in which the server confirmation hash is computed over
   the recovered session key concatenated with the server's
   identifier.  Binding the digest to the server identifier ensures
   that a valid confirmation produced by one server cannot be
   replayed as a confirmation by any other server that happens to
   share the same hash function and key space, regardless of which
   long-term public key is in use.

   The client generates a fresh symmetric session key, encrypts it
   under the server's long-term public key pk(S), and transmits the
   resulting ciphertext.  The server S decrypts the ciphertext and
   returns h(<k, S>) as confirmation.  The client recomputes
   h(<k, S>) for its own k and the intended server identifier S,
   and accepts the run on match.

2. Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   The following notation is used throughout this document.

      C, S         The client and the server.  S also denotes the
                   server's identifier as a public, deployment-scoped
                   octet string.
      sk(S), pk(S) The long-term private and public key bound to the
                   server identifier S.
      k            A fresh, uniformly random session key drawn by C.
      aenc, adec   Asymmetric encryption and decryption.
      h(x)         A one-way hash function applied to the encoding
                   of x.
      <a, b>       The ordered concatenation of a and b under a
                   canonical encoding.

3. Protocol Overview

         Client                                       Server
         ------                                       ------
         k  = fresh random
         m1 = aenc(k, pk(S))
                          ----- m1 ----->
                                                k  = adec(.,sk(S))
                                                m2 = h(<k, S>)
                          <---- m2 ------
         verify m2 == h(<k, S>)

   On successful completion both parties hold the same session key
   k and the client has confirmed that the holder of sk(S) is the
   server identified by S.

4. Message Format

   The KeyTransport message m1 carries the asymmetric encryption of
   the session key.

      struct {
          opaque ciphertext<1..2^16-1>;
      } KeyTransport;

   The KeyConfirm message m2 carries the server-bound one-way hash
   of the recovered session key.

      struct {
          opaque digest<1..2^8-1>;
      } KeyConfirm;

   The digest field is computed as h(encode(<k, S>)) where encode
   is a deterministic concatenation function fixed at the
   granularity of a single deployment, S is the server identifier,
   and h is the negotiated hash function.

5. Processing Rules

   On initiation, C selects the intended server identifier S,
   retrieves pk(S) by means defined elsewhere, generates k
   uniformly at random, computes ciphertext = aenc(k, pk(S)),
   constructs m1, and transmits m1 to S.  C retains the pair
   (S, k) pending receipt of the corresponding KeyConfirm message.

   On receipt of m1, S computes k' = adec(ciphertext, sk(S)).  If
   decryption fails or yields a value that does not conform to the
   expected key format, S MUST discard m1 and abort the run.
   Otherwise S computes digest = h(<k', S>) using its own
   identifier, constructs m2, and transmits m2 to C.

   On receipt of m2, C computes h(<k, S>) for the retained pair
   (S, k) and compares it for equality with m2.digest.  If the
   values match, C MAY consider k to be accepted by S; otherwise
   C MUST discard k and abort the run.

6. Security Considerations

   Confidentiality of the session key against a network adversary
   that does not hold sk(S) follows from the IND-CCA security of
   the underlying asymmetric scheme and the preimage resistance of
   h.  The server identifier S is public and contributes nothing
   to confidentiality.

   Server authentication is established by the fact that no party
   other than the holder of sk(S) is able to compute h(<k, S>)
   without first recovering k.  The protocol does not authenticate
   C.

   Inclusion of S in the hash input prevents a confirmation digest
   produced by one server from being replayed as a confirmation
   issued by any other server.  An adversary that operates a
   second server S' under the same key space cannot construct a
   confirmation digest that C will accept for the run intended for
   S, because the digest input is bound to S.

   Replay of a previously observed KeyTransport message causes S
   to recompute the same digest; because k is fresh in every run,
   a replay cannot cause C to accept a session key it did not
   itself generate.

   The protocol does not provide forward secrecy with respect to
   compromise of sk(S).  Implementations that require forward
   secrecy SHOULD compose this protocol with an ephemeral key
   agreement step.

   Implementations should be aware that the server identifier
   appears on the wire only as input to a one-way hash and so the
   protocol does not by itself provide identity confidentiality
   beyond what the underlying transport offers.
