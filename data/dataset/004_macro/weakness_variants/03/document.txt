   Public-Key Session Key Transport with Unbound Confirm Check
                       draft-famed-bsktunbound-00

Abstract

   This document specifies a public-key session key transport
   protocol in which the client conveys a freshly generated session
   key to a server using the server's long-term public key, and
   accepts the run after receiving from the network a value v
   together with the one-way hash h(v).  The check performed by
   the client is the structural consistency of the received pair;
   the value v is not bound to the session key actually
   transported.

1. Introduction

   This document defines a minimal public-key session key transport
   exchange in which the client unilaterally selects a fresh session
   key, transmits it under the server's public key, and accepts the
   run upon receipt of a pair (v, d) such that d equals the one-way
   hash of v.  The value v received in the reply is not constrained
   to equal the session key transmitted by C; the check at C
   verifies only the internal consistency of the pair.

   The protocol is intended for environments in which a coarse
   well-formedness check on the reply is desired but the calling
   application accepts that the reply is not cryptographically
   bound to the transmitted session key.

2. Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   and "OPTIONAL" in this document are to be interpreted as described
   in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in
   all capitals, as shown here.

   The following notation is used throughout this document.

      C, S         The client and the server.
      sk(S), pk(S) The long-term private and public key of S.
      k            A fresh, uniformly random session key drawn by C.
      v            An octet string carried in the reply alongside
                   its one-way hash.
      aenc, adec   Asymmetric encryption and decryption.
      h(x)         A one-way hash function applied to x.
      <a, b>       The ordered concatenation of a and b.

3. Protocol Overview

   The protocol consists of two messages exchanged between C and S.

         Client                                       Server
         ------                                       ------
         k  = fresh random
         m1 = aenc(k, pk(S))
                          ----- m1 ----->
                                                k = adec(.,sk(S))
                                                m2 = <k, h(k)>
                          <---- m2 ------
         parse m2 as <v, d>
         verify d == h(v)
         accept k

   On successful completion C accepts k as the session key
   provided that the inbound reply parses as a pair whose second
   component is the one-way hash of the first.

4. Message Format

   The KeyTransport message m1 carries the asymmetric encryption of
   the session key.

      struct {
          opaque ciphertext<1..2^16-1>;
      } KeyTransport;

   The KeyConfirm message m2 carries an octet string v together
   with its one-way hash.

      struct {
          opaque value<1..2^16-1>;
          opaque digest<1..2^8-1>;
      } KeyConfirm;

5. Processing Rules

   On initiation, C generates k uniformly at random, computes
   ciphertext = aenc(k, pk(S)), constructs m1, and transmits m1 to
   S.  C retains k locally as the session key.

   On receipt of m1, S computes k' = adec(ciphertext, sk(S)),
   constructs m2 with value field set to k' and digest field set
   to h(k'), and transmits m2 to C.

   On receipt of a candidate m2, C parses m2 as a pair (v, d) and
   computes h(v) over the value field as received.  If the
   computed h(v) equals d, C MAY consider the run as completed
   and accept k as the session key.  Otherwise C MUST discard the
   run.

6. Security Considerations

   This protocol verifies the internal consistency of the inbound
   reply but does not bind the reply to the session key actually
   transmitted by C.  Implementations should be aware that this
   relaxation has consequences for the cryptographic properties
   that the protocol can provide.

   The protocol does not authenticate the server.  Acceptance of
   the session key at C is conditioned only on the arrival of a
   pair (v, d) for which d equals h(v); any party that is able to
   choose an arbitrary v and to compute h(v) over its own choice
   can construct such a pair, and no party is required to
   demonstrate possession of sk(S) in order to cause C to accept
   k.  An adversary that injects a fabricated pair (v, h(v)) in
   place of the genuine reply causes C to complete the run with k
   without the holder of sk(S) ever having processed the
   corresponding KeyTransport.

   Confidentiality of k against a network adversary that does not
   hold sk(S) follows from the IND-CCA security of the underlying
   asymmetric scheme; the absence of binding between v and k in
   the confirmation check does not, by itself, expose k to such
   an adversary.  Operators that rely on the protocol for key
   transport SHOULD therefore not assume any guarantee beyond the
   secrecy of k against passive observation.

   The protocol does not provide forward secrecy with respect to
   compromise of sk(S).  Implementations that require forward
   secrecy SHOULD compose this protocol with an ephemeral key
   agreement step.

   Implementations that require evidence that S has processed the
   transmitted KeyTransport before using k MUST add a separate
   confirmation step that binds the reply to the session key
   transmitted by C; this document does not specify such a step.
