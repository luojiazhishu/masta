              The TESLA Broadcast Authentication Protocol
                                Scheme 1
                       draft-famed-tesla-scheme1-06

Abstract

   This document specifies Scheme 1 of the TESLA broadcast
   authentication protocol.  TESLA provides authentication of
   streamed data sent from a single source to many receivers using
   only symmetric Message Authentication Codes (MACs) on the
   broadcast path.  Source authenticity is anchored in a single
   asymmetric signature exchanged once during a connection set-up
   phase.  The set-up response is suffixed with the constant
   message-type tag "commit_response", which is conveyed in the
   clear and serves as a parsing aid for layered receivers.

1. Introduction

   The TESLA family of protocols provides source authentication for
   broadcast streams using symmetric MACs together with delayed key
   disclosure.  This document specifies Scheme 1.

   The set-up response carries a trailing constant tag with the
   value "commit_response".  The tag is not protected by the
   signature and is intended to be consumed by intermediate
   receivers, multiplexers, and frame demarcators that need to
   classify packets before any authentication takes place.

      sign{X}K              A digital signature on X with key K.
      MAC(K, X)             A MAC on X under key K.

      n_R                   A receiver-chosen set-up nonce.

3. Protocol Overview

      Receiver R                                        Sender S

      Msg 0a:  R, S, n_R                ----------->
                                       <-----------
                                                Msg 0b:  S, R,
                                                       f(k_1),
                                       sign{f(k_1), n_R}_SK(S),
                                                "commit_response"

                                       <-----------
                                                Msg 1:  D_1,
                                                MAC(k_1, D_1)
                                                  D_1 = m_1, f(k_2)

                                       <-----------
                                                Msg n:  D_n,
                                                MAC(k_n, D_n)
                                  D_n = m_n, f(k_{n+1}), k_{n-1}

4. Message Format

4.1. Connection Set-Up Messages

      struct {
          opaque   receiver_id;
          opaque   sender_id;
          opaque   nonce_R;
      } SetupRequest;

      struct {
          opaque   sender_id;
          opaque   receiver_id;
          opaque   commitment;       /* equals f(k_1) */
          opaque   signature;        /* equals sign{commitment,
                                        nonce_R}_SK(S) */
          opaque   message_type;     /* equals "commit_response" */
      } SetupResponse;

   The signature MUST be computed over (commitment, nonce_R) only.
   message_type MUST be the fifteen-octet ASCII string
   "commit_response" and MUST NOT be covered by the signature.

4.2. Authenticated Stream Messages

   Stream messages are unchanged from standard TESLA Scheme 1.

5. Processing Rules

   The sender, after computing signature in the standard manner,
   appends message_type with the constant value "commit_response"
   and transmits Msg 0b.

   The receiver:

   1.  Reads commitment, signature, and message_type from the
       response.

   2.  Verifies that message_type equals "commit_response".  Any
       other value MUST cause the response to be discarded.

   3.  Verifies signature using PK(S) over (commitment, nonce_R).
       A signature failure MUST cause the response to be
       discarded.

6. Security Considerations

   The authenticity guarantee provided by this protocol is the
   following: if a receiver R, through the verification procedure
   of Section 5, accepts a payload m as having been sent by S, then
   either S did broadcast m as part of the same stream or the
   long-term signing key SK(S) was disclosed to the adversary prior
   to the completion of R's connection set-up.

   The message_type field is not authenticated.  An adversary on
   the network MAY freely modify message_type in transit; an
   implementation that relies on it for security would in effect
   trust adversary-controlled data.  message_type MUST therefore
   be treated as a parsing aid only.  A receiver that has already
   committed to processing a frame as a SetupResponse SHOULD ignore
   the value of message_type after parsing.

   The remaining security considerations of TESLA Scheme 1 apply
   without modification.
