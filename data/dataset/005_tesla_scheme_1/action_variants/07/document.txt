              The TESLA Broadcast Authentication Protocol
                                Scheme 1
                       draft-famed-tesla-scheme1-07

Abstract

   This document specifies Scheme 1 of the TESLA broadcast
   authentication protocol.  TESLA provides authentication of
   streamed data sent from a single source to many receivers using
   only symmetric Message Authentication Codes (MACs) on the
   broadcast path.  Source authenticity is anchored in a single
   asymmetric signature exchanged once during a connection set-up
   phase.  The first authenticated stream message carries a
   constant trailing marker, "data1_marker", that is conveyed in
   the clear and is intended to be consumed by demultiplexers that
   need to recognise the inaugural broadcast frame.

1. Introduction

   The TESLA family of protocols provides source authentication for
   broadcast streams using symmetric MACs together with delayed key
   disclosure.  This document specifies Scheme 1.

   The first stream message broadcast by the sender carries a
   trailing constant marker with the value "data1_marker".  The
   marker is conveyed in the clear, is not protected by the MAC,
   and is intended for use by demultiplexing receivers that need
   a low-cost way to identify the inaugural frame in the stream.

3. Protocol Overview

      Receiver R                                        Sender S

      Msg 0a:  R, S, n_R                ----------->
                                       <-----------
                                                Msg 0b:  S, R,
                                                       f(k_1),
                                       sign{f(k_1), n_R}_SK(S)

                                       <-----------
                                                Msg 1:  D_1,
                                                MAC(k_1, D_1),
                                                  "data1_marker"
                                                  D_1 = m_1, f(k_2)

                                       <-----------
                                                Msg n:  D_n,
                                                MAC(k_n, D_n)
                                  D_n = m_n, f(k_{n+1}), k_{n-1}

   Stream messages numbered 2 and above follow the standard Scheme
   1 layout and do not carry the marker.

4. Message Format

4.1. Connection Set-Up Messages

   Set-up messages are unchanged from standard TESLA Scheme 1.

4.2. Authenticated Stream Messages

   The first stream message has the following structure:

      struct {
          opaque   payload;          /* m_1 */
          opaque   next_commitment;  /* equals f(k_2) */
          opaque   mac;              /* equals
                                        MAC(k_1, <payload,
                                          next_commitment>) */
          opaque   marker;           /* equals "data1_marker" */
      } FirstStreamMessage;

   Subsequent stream messages have the standard Scheme 1
   structure.

   The MAC of the first stream message is computed over payload
   and next_commitment only; marker is excluded.  The marker MUST
   be the twelve-octet ASCII string "data1_marker".

5. Processing Rules

   The connection set-up phase is processed exactly as in standard
   TESLA Scheme 1.

   When sending the first stream message the sender:

   1.  Selects a fresh MAC key k_2 and a fresh payload m_1.

   2.  Forms D_1 = (m_1, f(k_2)).

   3.  Computes mac = MAC(k_1, D_1).

   4.  Broadcasts (D_1, mac, "data1_marker").

   When receiving the first stream message the receiver:

   1.  Reads D_1, mac, and marker from the broadcast.

   2.  Verifies that marker equals "data1_marker".  Frames carrying
       any other marker MUST be discarded.

   3.  Caches D_1 with mac for delayed verification, exactly as in
       standard Scheme 1.

   The handling of subsequent stream messages is unchanged.

6. Security Considerations

   The authenticity guarantee provided by this protocol is the
   following: if a receiver R, through the verification procedure
   of Section 5, accepts a payload m as having been sent by S, then
   either S did broadcast m as part of the same stream or the
   long-term signing key SK(S) was disclosed to the adversary prior
   to the completion of R's connection set-up.

   The marker field is not authenticated.  An adversary on the
   network MAY freely modify, replay, or fabricate marker values
   in transit; an implementation that rejects only on a marker
   mismatch provides no security benefit beyond standard frame
   parsing.  Receivers MUST treat marker as a parsing aid only.

   Implementations MUST refuse to accept any stream message for
   which the corresponding key could already have been disclosed at
   the time of receipt.  Confidentiality of the broadcast payload
   is out of scope.  Implementations MUST use a signature scheme
   with existential unforgeability under chosen message attack, a
   one-way function f with adequate preimage resistance, and a MAC
   algorithm that resists forgery without knowledge of the key.
