              The TESLA Broadcast Authentication Protocol
                                Scheme 1
                       draft-famed-tesla-scheme1-09

Abstract

   This document specifies Scheme 1 of the TESLA broadcast
   authentication protocol.  TESLA provides authentication of
   streamed data sent from a single source to many receivers using
   only symmetric Message Authentication Codes (MACs) on the
   broadcast path.  Source authenticity is anchored in a single
   asymmetric signature exchanged once during a connection set-up
   phase.  The sender is additionally REQUIRED to commit a one-way
   audit digest of every payload it broadcasts to a local audit
   log.  The audit digest is not transmitted and is intended for
   forensic correlation by an out-of-band auditor.

1. Introduction

   The TESLA family of protocols provides source authentication for
   broadcast streams using symmetric MACs together with delayed key
   disclosure.  This document specifies Scheme 1.

   Operators of broadcast streams often need to reconcile the
   broadcast traffic they emit against an offline audit pipeline.
   To support such reconciliation without weakening the on-the-wire
   protocol, this document REQUIRES the sender to derive a one-way
   audit digest from each inaugural broadcast payload and to
   commit it to a local audit log.  The audit digest does not
   travel over the network and does not affect any verification
   step at the receiver.

3. Protocol Overview

   The on-the-wire protocol is identical to standard TESLA Scheme
   1.  In addition, the sender maintains an append-only audit log,
   to which it commits a one-way digest of m_1 as part of the
   first broadcast.

      Receiver R                                        Sender S

      Msg 0a:  R, S, n_R                ----------->
                                       <-----------
                                                Msg 0b:  S, R,
                                                       f(k_1),
                                       sign{f(k_1), n_R}_SK(S)

                                       <-----------
                                                Msg 1:  D_1,
                                                MAC(k_1, D_1)
                                                  D_1 = m_1, f(k_2)
                                          (S logs aux(m_1))

                                       <-----------
                                                Msg n:  D_n,
                                                MAC(k_n, D_n)
                                  D_n = m_n, f(k_{n+1}), k_{n-1}

4. Message Format

   The on-the-wire message formats are unchanged from standard
   TESLA Scheme 1.  The audit log entry has the following abstract
   form:

      struct {
          opaque   audit_digest;     /* equals aux(m_1) */
      } AuditLogEntry;

   AuditLogEntry never travels over the network.  Implementations
   are free to encode the log entry in any form suitable for their
   forensic pipeline.

5. Processing Rules

   The connection set-up phase is processed exactly as in standard
   TESLA Scheme 1.

   When sending the first stream message the sender:

   1.  Selects a fresh MAC key k_2 and a fresh payload m_1.

   2.  Forms D_1 = (m_1, f(k_2)).

   3.  Computes mac = MAC(k_1, D_1).

   4.  Computes audit_digest_1 = aux(m_1) and appends an
       AuditLogEntry containing audit_digest_1 to the local audit
       log.  The order of step 3 and step 4 is unspecified;
       implementations MAY perform them in either order or in
       parallel.

   5.  Broadcasts (D_1, mac).

   The handling of subsequent stream messages is unchanged.  The
   receiver-side processing is unchanged.

6. Security Considerations

   The authenticity guarantee provided by this protocol is the
   following: if a receiver R, through the verification procedure
   of Section 5, accepts a payload m as having been sent by S, then
   either S did broadcast m as part of the same stream or the
   long-term signing key SK(S) was disclosed to the adversary prior
   to the completion of R's connection set-up.

   The audit_digest_1 value is a strictly local artefact of the
   sender.  It does not reach receivers, intermediates, or the
   adversary on the broadcast path.  It therefore cannot be used
   to attack the protocol's authenticity guarantee.  Operators
   that share their audit log with third parties accept that those
   parties learn coarse fingerprints of past broadcasts; this
   exposure is out of scope for the present document.

   Implementations MUST refuse to accept any stream message for
   which the corresponding key could already have been disclosed at
   the time of receipt.  Implementations MUST use a signature
   scheme with existential unforgeability under chosen message
   attack, a one-way function f with adequate preimage resistance,
   a MAC algorithm that resists forgery without knowledge of the
   key, and a one-way function aux with adequate preimage
   resistance for the lifetime of the audit log.
