              The TESLA Broadcast Authentication Protocol
                                Scheme 1
                       draft-famed-tesla-scheme1-11

Abstract

   This document specifies Scheme 1 of the TESLA broadcast
   authentication protocol.  TESLA provides authentication of
   streamed data sent from a single source to many receivers using
   only symmetric Message Authentication Codes (MACs) on the
   broadcast path.  Source authenticity is anchored in a single
   asymmetric signature exchanged once during a connection set-up
   phase.  The signature in the SetupResponse is computed over the
   first key commitment, the receiver-chosen nonce, and the
   constant domain-separation tag "init".

1. Introduction

   The TESLA family of protocols provides source authentication for
   broadcast streams using symmetric MACs together with delayed key
   disclosure.  This document specifies Scheme 1.

   The signature in the SetupResponse binds the first key
   commitment f(k_1) and the receiver's nonce n_R to a fixed
   domain-separation tag with the value "init".  Including the
   tag in the signed material ensures that signatures issued
   inside the TESLA set-up exchange cannot be confused with
   signatures issued by the same long-term key in any other
   protocol.

      sign{X}K           A digital signature on X with key K.
      MAC(K, X)          A MAC on X under key K.

      k_i, m_i, D_i      Standard TESLA Scheme 1 stream notation.

3. Protocol Overview

      Receiver R                                        Sender S

      Msg 0a:  R, S, n_R                ----------->
                                       <-----------
                                                Msg 0b:  S, R,
                                                       f(k_1),
                                       sign{f(k_1), n_R,
                                                  "init"}_SK(S)

                                       <-----------
                                                Msg 1:  D_1,
                                                MAC(k_1, D_1)
                                                  D_1 = m_1, f(k_2)

                                       <-----------
                                                Msg n:  D_n,
                                                MAC(k_n, D_n)
                                  D_n = m_n, f(k_{n+1}), k_{n-1}

4. Message Format

4.1. Connection Set-Up Messages

   Msg 0a (R -> S):

      struct {
          opaque   receiver_id;
          opaque   sender_id;
          opaque   nonce_R;
      } SetupRequest;

   Msg 0b (S -> R):

      struct {
          opaque   sender_id;
          opaque   receiver_id;
          opaque   commitment;       /* equals f(k_1) */
          opaque   signature;        /* equals sign{commitment,
                                        nonce_R, "init"}_SK(S) */
      } SetupResponse;

   The signature MUST be computed over the concatenation, in
   order, of commitment, nonce_R, and the four-octet ASCII string
   "init", using SK(S).

4.2. Authenticated Stream Messages

   Stream messages are unchanged from standard TESLA Scheme 1.

5. Processing Rules

   The sender, upon receiving a SetupRequest:

   1.  Reads nonce_R from the request.

   2.  Forms the SetupResponse with the commitment f(k_1).

   3.  Computes signature = sign{f(k_1), nonce_R, "init"}_SK(S).

   4.  Transmits Msg 0b on the network destined to R.

   The receiver, upon receiving a SetupResponse:

   1.  Verifies signature using PK(S) over (commitment, nonce_R,
       "init") where commitment is read from the response and
       nonce_R is the locally retained value previously sent in
       the SetupRequest.

   2.  If verification fails, the response MUST be discarded.

   The handling of the broadcast phase is unchanged.

6. Security Considerations

   The authenticity guarantee provided by this protocol is the
   following: if a receiver R, through the verification procedure
   of Section 5, accepts a payload m as having been sent by S, then
   either S did broadcast m as part of the same stream or the
   long-term signing key SK(S) was disclosed to the adversary prior
   to the completion of R's connection set-up.

   Binding the constant "init" inside the SetupResponse signature
   provides domain separation between TESLA set-up signatures and
   any other signature that S may legitimately produce with the
   same long-term key.  An adversary that obtains a signature in
   another context cannot replay it as a SetupResponse, because
   such a signature, by construction, does not cover the prefix
   "init" expected by the receiver.  Implementations MUST NOT use
   the constant "init" in the signed material of any other
   protocol that shares SK(S).

   Implementations MUST refuse to accept any stream message for
   which the corresponding key could already have been disclosed at
   the time of receipt.  Implementations MUST use a signature
   scheme with existential unforgeability under chosen message
   attack, a one-way function f with adequate preimage resistance,
   and a MAC algorithm that resists forgery without knowledge of
   the key.
