              The TESLA Broadcast Authentication Protocol
                                Scheme 1
                       draft-famed-tesla-scheme1-12

Abstract

   This document specifies Scheme 1 of the TESLA broadcast
   authentication protocol.  TESLA provides authentication of
   streamed data sent from a single source to many receivers using
   only symmetric Message Authentication Codes (MACs) on the
   broadcast path.  Source authenticity is anchored in a single
   asymmetric signature exchanged once during a connection set-up
   phase.  The MAC of every authenticated stream message is
   computed over the data block concatenated with the constant
   domain-separation tag "stream".

1. Introduction

   The TESLA family of protocols provides source authentication for
   broadcast streams using symmetric MACs together with delayed key
   disclosure.  This document specifies Scheme 1.

   The MAC of every authenticated stream message is computed over
   the data block concatenated with a fixed tag of value "stream".
   The tag provides domain separation between MACs computed by the
   broadcast path and any other MAC that might be issued under the
   same chain of keys, including any MAC the implementation might
   later choose to reuse for unrelated purposes.

2. Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when, they
   appear in all capitals, as shown here.

   Throughout this document:

      S, R               Sender and receiver.
      f(k)               The commitment to MAC key k.
      n_R                A receiver-chosen set-up nonce.
      "stream"           The constant ASCII domain-separation tag
                         bound under every stream MAC.
      k_i, m_i, D_i      Standard TESLA Scheme 1 stream notation.

3. Protocol Overview

      Receiver R                                        Sender S

      Msg 0a:  R, S, n_R                ----------->
                                       <-----------
                                                Msg 0b:  S, R,
                                                       f(k_1),
                                       sign{f(k_1), n_R}_SK(S)

                                       <-----------
                                       Msg 1:  D_1,
                                       MAC(k_1, <D_1, "stream">)
                                                  D_1 = m_1, f(k_2)

                                       <-----------
                                       Msg n:  D_n,
                                       MAC(k_n, <D_n, "stream">)
                                  D_n = m_n, f(k_{n+1}), k_{n-1}

   The MAC computation of every stream message includes the
   constant tag "stream" alongside the data block.

4. Message Format

4.1. Connection Set-Up Messages

   Set-up messages are unchanged from standard TESLA Scheme 1.

4.2. Authenticated Stream Messages

   The first stream message has the following structure:

      struct {
          opaque   payload;          /* m_1 */
          opaque   next_commitment;  /* equals f(k_2) */
          opaque   mac;              /* equals
                                        MAC(k_1,
                                            <<payload,
                                              next_commitment>,
                                             "stream">) */
      } FirstStreamMessage;

   Subsequent stream messages have the following structure:

      struct {
          opaque   payload;          /* m_i, i >= 2 */
          opaque   next_commitment;  /* equals f(k_{i+1}) */
          opaque   disclosed_key;    /* equals k_{i-1} */
          opaque   mac;              /* equals
                                        MAC(k_i,
                                            <<payload,
                                              next_commitment,
                                              disclosed_key>,
                                             "stream">) */
      } StreamMessage;

   The constant "stream" MUST be the six-octet ASCII string
   "stream".  The same constant MUST be used by every stream
   message in the broadcast.

5. Processing Rules

   The set-up phase is unchanged from standard TESLA Scheme 1.

   When sending the i-th stream message the sender:

   1.  Forms D_i exactly as in standard Scheme 1.

   2.  Computes mac = MAC(k_i, <D_i, "stream">).

   3.  Broadcasts (D_i, mac).

   When receiving a stream message the receiver caches D_i with
   mac as in standard Scheme 1.  When the disclosure of k_{i-1}
   later allows verification, the receiver recomputes
   MAC(k_{i-1}, <D_{i-1}, "stream">) and compares it with the
   cached mac.  Failure of the comparison MUST cause the cached
   payload to be discarded.

6. Security Considerations

   The authenticity guarantee provided by this protocol is the
   following: if a receiver R, through the verification procedure
   of Section 5, accepts a payload m as having been sent by S, then
   either S did broadcast m as part of the same stream or the
   long-term signing key SK(S) was disclosed to the adversary prior
   to the completion of R's connection set-up.

   Binding the constant "stream" inside every stream MAC provides
   domain separation between the broadcast MAC and any other MAC
   that might be issued under the same key chain.  An adversary
   that obtains a MAC in another context cannot replay it as a
   stream MAC, because such a MAC, by construction, does not
   cover the suffix "stream" expected by the receiver.
   Implementations MUST NOT use the constant "stream" in the MAC
   input of any other protocol that shares the key chain.

   Implementations MUST refuse to accept any stream message for
   which the corresponding key could already have been disclosed at
   the time of receipt.  Implementations MUST use a signature
   scheme with existential unforgeability under chosen message
   attack, a one-way function f with adequate preimage resistance,
   and a MAC algorithm that resists forgery without knowledge of
   the key.
