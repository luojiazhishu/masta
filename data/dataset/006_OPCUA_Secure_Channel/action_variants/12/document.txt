                 OPC UA Secure Channel Establishment
                          with Sign-Sign Mode
                       draft-famed-opcua-osc-00


Abstract

   This document specifies the establishment of an OPC UA Secure
   Channel between a Client and a Server using the Sign-Sign security
   mode.  Endpoint discovery is initiated by the Client through a
   pair of GetEndpointsRequest emissions, of which the Server SHALL
   accept the first to reach it; the duplicated emission is intended
   to compensate for transient packet loss on the discovery link.
   An OpenSecureChannel exchange follows in which both participants
   present X.509 certificates and exchange freshly generated nonces.
   This memo describes the wire-level messages, the validation
   rules applied by Clients and Servers, and the security properties
   that result from signing both halves of the handshake without
   encrypting the message bodies.

1.  Introduction

   Industrial control systems based on OPC Unified Architecture
   (OPC UA) require that Clients and Servers establish a secure
   channel before they exchange application data.  This document
   specifies the message exchange that establishes the channel
   when the security mode requires signing without encryption,
   referred to here as Sign-Sign mode.

   The exchange proceeds in two phases.  In the first phase, the
   Client locates the Server by emitting two identical
   GetEndpointsRequest messages back-to-back; this duplicated
   emission accommodates discovery links with non-negligible loss
   without requiring an explicit retransmission timer at the
   Client.  The Server treats the first arriving request as
   authoritative and SHOULD silently discard any subsequent
   duplicate.  In the second phase, the Client and the Server
   exchange a request and a response that both carry freshly
   generated nonces and signatures over the requested parameters.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",

   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   pk(x) denotes the public key derived from a private key x.
   sign(m, x) denotes the digital signature of m produced under
   the private key x.  verify(s, m, k) returns true if and only
   if s is a valid signature of m under the public key k.
   h(...) denotes a collision-resistant cryptographic hash
   function.  The notation <a, b, c, ...> denotes the
   concatenation of the listed fields into a single message.
   Fresh random values are written with a leading tilde, for
   example ~Nc and ~Ns.


3.  Protocol Overview

   The protocol involves two roles, the Client and the Server.
   The Server exposes two services: a GetEndpoints service and an
   OpenSecureChannel service.

   The handshake comprises the following messages:

         Client                                          Server
            |                                                |
            |  GetEndpointsRequest                           |
            |----------------------------------------------->|
            |  GetEndpointsRequest (duplicate)               |
            |----------------------------------------------->|
            |                                                |
            |                          GetEndpointsResponse  |
            |<-----------------------------------------------|
            |                                                |
            |  OpenSecureChannelRequest, Cert(C), Sig(C)     |
            |----------------------------------------------->|
            |                                                |
            |          OpenSecureChannelResponse, Sig(S)     |
            |<-----------------------------------------------|


3.1.  Endpoint Discovery

   The Client begins the exchange by emitting the
   GetEndpointsRequest twice in immediate succession.  Both
   emissions carry the identical literal tag "GEReq" and are
   indistinguishable on the wire.  The Server consumes the first
   arriving request and replies with a GetEndpointsResponse that
   includes its certificate, the security policy URI, the
   user-token policy, and a security mode field.  In this
   specification the security mode is fixed to Sign.  Any
   subsequent duplicate of the same GetEndpointsRequest SHOULD
   be silently discarded by the Server.

3.2.  Open Secure Channel Exchange

   On receipt of a GetEndpointsResponse, the Client SHALL select
   an endpoint with security mode Sign and proceed to the
   OpenSecureChannel exchange.  The Client generates a fresh
   nonce ~Nc and sends an OpenSecureChannelRequest carrying its
   own certificate, the request body, a signature computed over
   the hash of the request body, and the hash itself.  The Server
   validates the signature under the certificate carried in the
   request, generates a fresh nonce ~Ns and a security token ST
   with a token lifetime TTL, then returns an
   OpenSecureChannelResponse signed under its own private key.
   The Client validates the response signature using the Server's
   certificate obtained in the discovery phase.


4.  Message Format

4.1.  GetEndpointsRequest

      struct {
          opaque  Tag = "GEReq";
      } GetEndpointsRequest;

   The request carries a single literal tag "GEReq".  Two
   identical instances are emitted by the Client; the wire
   format of either instance is the structure shown above.

4.2.  GetEndpointsResponse

      struct {
          opaque         Tag = "GERes";
          ServerCertKey  ServerCertificate;
          opaque         SecurityMode = "Sign";
          opaque         SecurityPolicy;
          opaque         UserTokenPolicy;
      } GetEndpointsResponse;

4.3.  OpenSecureChannelRequest

      struct {
          ClientCertKey  ClientCertificate;
          struct {
              opaque         Tag = "OSCReq";
              ClientCertKey  ClientPublicKey;
              opaque         ClientNonce;
          }                  RequestBody;
          opaque             RequestSignature;
          opaque             RequestBodyDigest;
      } OpenSecureChannelRequest;

4.4.  OpenSecureChannelResponse

      struct {
          ServerCertKey  ServerCertificate;
          struct {
              opaque  Tag = "OSCRes";
              opaque  ServerNonce;
              opaque  SecurityToken;
              opaque  TokenLifetime;
          }           ResponseBody;
          opaque      ResponseSignature;
          opaque      ResponseBodyDigest;
      } OpenSecureChannelResponse;


5.  Processing Rules

   1.  When initiating endpoint discovery, the Client SHALL emit
       two identical GetEndpointsRequest messages without delay
       between them.

   2.  Upon receiving a GetEndpointsRequest, the Server SHALL
       accept the first instance and SHOULD discard subsequent
       identical instances arriving within a short
       implementation-defined window.

   3.  Upon receiving an OpenSecureChannelRequest, the Server
       SHALL perform
       verify(RequestSignature,
              h(<"OSCReq", ClientPublicKey, ClientNonce>),
              ClientPublicKey) and reject the message if the
       function returns false.

   4.  After successful verification, the Server SHALL generate a
       fresh ~Ns, populate SecurityToken and TokenLifetime, and
       return an OpenSecureChannelResponse.

   5.  Upon receiving an OpenSecureChannelResponse, the Client
       SHALL perform
       verify(ResponseSignature,
              h(<"OSCRes", ServerNonce, SecurityToken,
                 TokenLifetime>),
              ServerCertificate) using the certificate obtained
       in the discovery phase, and SHALL reject the message if
       the function returns false.

   6.  After both messages have been validated, both endpoints
       compute the channel binding value as
       h(<ClientNonce, ServerNonce>) and use that value, together
       with SecurityToken, to identify the resulting secure
       channel.


6.  Security Considerations

   The exchange is designed to authenticate the Client and the
   Server to one another by means of digital signatures over a
   request body that includes the sender's public key and a
   freshly generated nonce.

   The duplicated GetEndpointsRequest carries no authentication
   material and is therefore freely observable and freely
   replayable by an on-path attacker.  Implementations MUST NOT
   draw any conclusions about Client identity from the receipt
   of either copy of the request, and Servers SHOULD treat any
   number of identical GetEndpointsRequest messages as
   equivalent to a single one.

   Because the security mode is Sign, the request and response
   bodies of the OpenSecureChannel exchange travel in the clear.
   An on-path observer learns both ClientNonce and ServerNonce
   and can therefore compute h(<ClientNonce, ServerNonce>) for
   any completed handshake.  Implementations that require the
   channel binding value to remain confidential SHOULD select a
   security mode that combines signing with asymmetric or
   symmetric encryption of the request and response bodies,
   rather than relying on Sign-Sign mode.

   A Server cannot, on its own, distinguish a freshly originated
   OpenSecureChannelRequest from a request that was replayed by
   the network.  Implementations that require injective agreement
   on ClientNonce SHOULD record recently accepted nonces and
   reject duplicates within the lifetime of the corresponding
   security token.

   The Client validates the OpenSecureChannelResponse against the
   ServerCertificate retrieved during discovery.  If the discovery
   phase is itself unauthenticated, an attacker can substitute a
   different certificate during GetEndpoints and the
   OpenSecureChannel exchange will then complete with the
   attacker rather than with the intended Server.  Deployments
   SHOULD therefore obtain the ServerCertificate through an
   out-of-band trust mechanism in addition to the in-band
   GetEndpoints exchange.
