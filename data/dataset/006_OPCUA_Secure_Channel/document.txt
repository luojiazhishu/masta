                 OPC UA Secure Channel Establishment
                          with Sign-Sign Mode
                       draft-famed-opcua-osc-00


Abstract

   This document specifies the establishment of an OPC UA Secure
   Channel between a Client and a Server using the Sign-Sign security
   mode.  The procedure consists of an endpoint discovery exchange
   followed by an OpenSecureChannel exchange in which both
   participants present X.509 certificates and exchange freshly
   generated nonces.  The pair of nonces is bound to the subsequent
   secure channel through a hash-based derivation step.  This memo
   describes the wire-level messages, the validation rules applied by
   Clients and Servers, and the security properties that result from
   signing both halves of the handshake without encrypting the
   message bodies.

1.  Introduction

   Industrial control systems based on OPC Unified Architecture
   (OPC UA) require that Clients and Servers establish a secure
   channel before they exchange application data.  The secure
   channel is bound to a pair of certificates, a security policy,
   and a security mode.  This document specifies the message
   exchange that establishes the channel when the security mode
   requires signing without encryption, referred to here as
   Sign-Sign mode.

   The exchange proceeds in two phases.  In the first phase, the
   Client locates the Server and obtains the Server's endpoint
   description, which carries the Server's certificate and the list
   of acceptable security policies.  In the second phase, the
   Client and the Server exchange a request and a response that
   both carry freshly generated nonces and signatures over the
   requested parameters.  Once the exchange completes, both peers
   compute a channel binding value from the two nonces that
   identifies the resulting secure channel.

   This memo describes the wire-level messages and the processing
   rules applied by each role.  It does not redefine the abstract
   service interface or the OPC UA encoding, which are documented
   in [OPCUA-Part4] and [OPCUA-Part6].


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL

   they appear in all capitals, as shown here.

2.2.  Notation

   Cryptographic operations are written as follows.  pk(x) denotes
   the public key derived from a private key x.  sign(m, x) denotes
   the digital signature of the message m produced under the
   private key x.  verify(s, m, k) returns true if and only if s is
   a valid signature of m under the public key k.  h(...) denotes
   a collision-resistant cryptographic hash function applied to its
   argument tuple.  The notation <a, b, c, ...> denotes the
   concatenation of the listed fields into a single message.
   Fresh random values generated by an endpoint are written with a
   leading tilde, for example ~Nc and ~Ns.


3.  Protocol Overview

   The protocol involves two roles, the Client and the Server.
   The Server exposes two services: a GetEndpoints service that
   returns endpoint descriptions, and an OpenSecureChannel service
   that accepts requests to establish a secure channel.  Both
   services MAY be hosted by the same Server instance.

   The handshake comprises the following messages:

         Client                                          Server
            |                                                |
            |  GetEndpointsRequest                           |
            |----------------------------------------------->|
            |                                                |
            |                          GetEndpointsResponse  |
            |<-----------------------------------------------|
            |                                                |
            |  OpenSecureChannelRequest, Cert(C), Sig(C)     |
            |----------------------------------------------->|
            |                                                |
            |          OpenSecureChannelResponse, Sig(S)     |
            |<-----------------------------------------------|


3.1.  Endpoint Discovery

   The Client begins the exchange by sending a
   GetEndpointsRequest to the Server.  The request does not carry
   any cryptographic material; it identifies the discovery
   service.  The Server replies with a GetEndpointsResponse that
   includes its certificate, the security policy URI, the
   user-token policy, and a security mode field.  In this
   specification the security mode is fixed to Sign.

3.2.  Open Secure Channel Exchange

   On receipt of a GetEndpointsResponse, the Client SHALL select
   an endpoint with security mode Sign and proceed to the
   OpenSecureChannel exchange.  The Client generates a fresh
   nonce ~Nc and sends an OpenSecureChannelRequest carrying its
   own certificate, the request body, a signature computed over
   the hash of the request body, and the hash itself.  The Server
   validates the signature under the certificate carried in the
   request, generates a fresh nonce ~Ns and a security token ST
   with a token lifetime TTL, then returns an
   OpenSecureChannelResponse signed under its own private key.
   The Client validates the response signature using the Server's
   certificate obtained in the discovery phase.


4.  Message Format

   The wire format of each message is given below using a
   struct-like notation.  Field names follow the OPC UA
   convention.

4.1.  GetEndpointsRequest

      struct {
          opaque  Tag = "GEReq";
      } GetEndpointsRequest;

   The request carries a single literal tag "GEReq".

4.2.  GetEndpointsResponse

      struct {
          opaque         Tag = "GERes";
          ServerCertKey  ServerCertificate;
          opaque         SecurityMode = "Sign";
          opaque         SecurityPolicy;
          opaque         UserTokenPolicy;
      } GetEndpointsResponse;

   ServerCertificate carries the Server's public key.
   SecurityPolicy and UserTokenPolicy are public identifiers of
   the policies acceptable to the Server.

4.3.  OpenSecureChannelRequest

      struct {
          ClientCertKey  ClientCertificate;
          struct {
              opaque         Tag = "OSCReq";
              ClientCertKey  ClientPublicKey;
              opaque         ClientNonce;
          }                  RequestBody;
          opaque             RequestSignature;
          opaque             RequestBodyDigest;
      } OpenSecureChannelRequest;

   ClientNonce is a freshly generated random value.
   RequestSignature is computed as sign(h(RequestBody), sk(C)).
   RequestBodyDigest is the value h(RequestBody); it is carried
   alongside the signature to bind the request body to the
   signature in deployments where the verifier prefers to operate
   on the digest rather than on the body itself.

4.4.  OpenSecureChannelResponse

      struct {
          ServerCertKey  ServerCertificate;
          struct {
              opaque  Tag = "OSCRes";
              opaque  ServerNonce;
              opaque  SecurityToken;
              opaque  TokenLifetime;
          }           ResponseBody;
          opaque      ResponseSignature;
          opaque      ResponseBodyDigest;
      } OpenSecureChannelResponse;

   ServerNonce is a freshly generated random value.
   SecurityToken identifies the channel and TokenLifetime gives
   the token's expiry interval in milliseconds.
   ResponseSignature is computed as sign(h(ResponseBody), sk(S)).
   ResponseBodyDigest is the value h(ResponseBody).


5.  Processing Rules

   1.  Upon sending an OpenSecureChannelRequest, the Client SHALL
       retain ~Nc until either an OpenSecureChannelResponse
       arrives or a local timeout expires.

   2.  Upon receiving an OpenSecureChannelRequest, the Server
       SHALL perform
       verify(RequestSignature,
              h(<"OSCReq", ClientPublicKey, ClientNonce>),
              ClientPublicKey) and reject the message if the
       function returns false.

   3.  After successful verification, the Server SHALL generate a
       fresh ~Ns, populate SecurityToken and TokenLifetime, and
       return an OpenSecureChannelResponse.

   4.  Upon receiving an OpenSecureChannelResponse, the Client
       SHALL perform
       verify(ResponseSignature,
              h(<"OSCRes", ServerNonce, SecurityToken,
                 TokenLifetime>),
              ServerCertificate) using the certificate obtained in
       the discovery phase, and SHALL reject the message if the
       function returns false.

   5.  After both messages have been validated, both endpoints
       compute the channel binding value as
       h(<ClientNonce, ServerNonce>) and use that value, together
       with SecurityToken, to identify the resulting secure
       channel.


6.  Security Considerations

   The exchange is designed to authenticate the Client and the
   Server to one another by means of digital signatures over a
   request body that includes the sender's public key and a
   freshly generated nonce.  The signatures bind the
   ClientPublicKey to the ClientNonce and bind the ServerNonce to
   the SecurityToken issued by the Server.  Implementations are
   responsible for checking that the certificate carried in the
   handshake corresponds to the public key that recomputed the
   request or response digest.

   Because the security mode is Sign, the request and response
   bodies travel in the clear.  An on-path observer learns both
   ClientNonce and ServerNonce and can therefore compute
   h(<ClientNonce, ServerNonce>) for any completed handshake.
   Implementations that require the channel binding value to
   remain confidential SHOULD select a security mode that
   combines signing with asymmetric or symmetric encryption of
   the request and response bodies, rather than relying on
   Sign-Sign mode.

   A Server cannot, on its own, distinguish a freshly originated
   OpenSecureChannelRequest from a request that was replayed by
   the network.  Implementations that require injective agreement
   on ClientNonce SHOULD record recently accepted nonces and
   reject duplicates within the lifetime of the corresponding
   security token.  Without such a replay cache, two distinct
   server-side sessions may share the same ClientNonce.

   The Client validates the OpenSecureChannelResponse against the
   ServerCertificate retrieved during discovery.  If the discovery
   phase is itself unauthenticated, an attacker can substitute a
   different certificate during GetEndpoints and the
   OpenSecureChannel exchange will then complete with the
   attacker rather than with the intended Server.  Deployments
   SHOULD therefore obtain the ServerCertificate through an
   out-of-band trust mechanism, such as a configured trust list,
   in addition to the in-band GetEndpoints exchange.

   This document does not specify confidentiality of the
   application data exchanged after the handshake; that
   protection MUST be negotiated through the SecurityToken and
   the security mode of the application channel.  Long-term
   private keys are assumed to be held in tamper-resistant
   storage and are out of scope for this memo.
