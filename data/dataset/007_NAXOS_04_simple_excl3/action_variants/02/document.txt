              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  Message 2
   carries the Responder's hashed ephemeral group element together
   with a freshly generated session correlator that the Responder
   uses to log and trace the issued response.  This memo describes
   the wire-level messages, the processing rules applied by
   Initiator and Responder, and the security properties that
   result from the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  The Responder
   augments Message 2 with a freshly generated SessionCorrelator
   in its outer envelope so that the Responder can index issued
   responses in its server-side trace.

   The protocol assumes a Dolev-Yao adversary that controls the
   network and is allowed to compromise the long-term secret of
   any party that is not directly involved in the run under
   consideration.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g, x^y, lk(P), ~eskI, ~eskR, h1, h2 are as defined for the
   Diffie-Hellman group.  Fresh random values are written with a
   leading tilde, including ~SessionCorrelator.


3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |  <hkR, ~SessionCorrelator>                     |
            |  hkR = g^h1(~eskR, lk(R))                      |
            |<-----------------------------------------------|


4.  Message Format

      struct {
          opaque  HashedEphemeral;   // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;   // hkR
          opaque  SessionCorrelator; // ~SessionCorrelator
      } Message2;


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL emit
       Message 1 carrying hkI = g^h1(~eskI, lk(I)).

   2.  Upon receiving Message 1, the Responder SHALL generate a
       fresh ~eskR and a fresh ~SessionCorrelator, compute
       hkR = g^h1(~eskR, lk(R)), and emit Message 2 as the pair
       <hkR, ~SessionCorrelator>.  The Responder SHALL compute
       the session key as
       kR = h2(<g^lk(I)^exR, X^lk(R), I, R>).

   3.  Upon receiving Message 2, the Initiator SHALL extract
       SessionCorrelator from the outer envelope without
       interpretation, treat the inner element as Y, and compute
       the session key as
       kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>).


6.  Security Considerations

   The session key derived by both parties is the output of a
   cryptographic hash over two Diffie-Hellman shared secrets.
   SessionCorrelator is a transport correlator only; it does not
   enter the input of h1 or h2 and SHALL NOT be relied upon as
   authentication evidence.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
   Implementations that require resistance to ephemeral-key
   leakage SHOULD use the full NAXOS construction.
