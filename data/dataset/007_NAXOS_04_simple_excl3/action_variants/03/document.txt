              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  Message 2
   carries the Responder's hashed ephemeral group element together
   with the literal protocol-version tag "NAXOS-v1", allowing
   message dispatchers to discriminate Message 2 from later
   revisions of this exchange without parsing the cryptographic
   payload.  This memo describes the wire-level messages, the
   processing rules applied by Initiator and Responder, and the
   security properties that result from the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  The outer
   envelope of Message 2 carries the literal wire-format version
   "NAXOS-v1" so that intermediaries and the receiving Initiator
   can identify the message at a glance.

   The protocol assumes a Dolev-Yao adversary that controls the
   network and is allowed to compromise the long-term secret of
   any party that is not directly involved in the run under
   consideration.

3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |  <hkR, "NAXOS-v1">                             |
            |  hkR = g^h1(~eskR, lk(R))                      |
            |<-----------------------------------------------|


4.  Message Format

      struct {
          opaque  HashedEphemeral;     // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;     // hkR
          opaque  WireFormatVersion = "NAXOS-v1";
      } Message2;


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL emit
       Message 1 carrying hkI = g^h1(~eskI, lk(I)).

   2.  Upon receiving Message 1, the Responder SHALL generate a
       fresh ~eskR, compute hkR = g^h1(~eskR, lk(R)), and emit
       Message 2 as the pair <hkR, "NAXOS-v1">.  The Responder
       SHALL compute the session key as
       kR = h2(<g^lk(I)^exR, X^lk(R), I, R>).

   3.  Upon receiving Message 2, the Initiator SHALL check that
       the WireFormatVersion field equals "NAXOS-v1", treat the
       inner element as Y, and compute the session key as
       kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>).


6.  Security Considerations

   The session key derived by both parties is the output of a
   cryptographic hash over two Diffie-Hellman shared secrets.
   The WireFormatVersion field is a public, fixed-value tag.  It
   does not enter the input of h1 or h2 and SHALL NOT be relied
   upon as authentication evidence.  Implementations MUST NOT
   treat its presence as evidence of Responder authenticity.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
   Implementations that require resistance to ephemeral-key
   leakage SHOULD use the full NAXOS construction.
