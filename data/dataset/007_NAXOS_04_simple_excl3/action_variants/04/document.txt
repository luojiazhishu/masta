              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  Before
   sending Message 1, the Initiator derives a local audit value
   that binds the Initiator and Responder identities together; the
   value is recorded in the local audit log for operator
   inspection but is not transmitted.  This memo describes the
   wire-level messages, the processing rules applied by Initiator
   and Responder, and the security properties that result from
   the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  Before
   constructing Message 1, the Initiator derives a local
   commitment that binds the Initiator identity to the intended
   Responder identity and writes the value to a client-side
   audit log.  This derivation supports deployment monitoring
   without affecting the cryptographic processing of the
   handshake.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g, x^y, lk(P), ~eskI, ~eskR, h1, h2 are as defined for the
   Diffie-Hellman group.

2.3.  Local Diagnostic Functions

   One opaque function is referenced in the Initiator processing
   rules of this specification:

   o  com(a, b) is a binding commitment over two arguments and is
      used by the Initiator to record a local audit value that
      ties the Initiator identity to the intended Responder
      identity at the moment of session initiation.

   The exact algorithm used to realise com is a local matter.
   Its output is not transmitted, is not part of any encrypted
   value, and does not appear in any wire-format message.


3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |              hkR = g^h1(~eskR, lk(R))          |
            |<-----------------------------------------------|


4.  Message Format

      struct {
          opaque  HashedEphemeral;   // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;   // hkR
      } Message2;


5.  Processing Rules

   1.  Before sending Message 1, the Initiator SHALL look up
       its own long-term secret lk(I), generate a fresh ~eskI,
       and SHALL compute the local audit value
       AuditCommitment = com(I, R).  AuditCommitment SHALL be
       retained in the local audit log; the value is not
       transmitted.

   2.  The Initiator SHALL emit Message 1 carrying
       hkI = g^h1(~eskI, lk(I)).

   3.  Upon receiving Message 1, the Responder SHALL generate a
       fresh ~eskR, compute hkR = g^h1(~eskR, lk(R)), and emit
       Message 2 carrying hkR.  The Responder SHALL compute the
       session key as
       kR = h2(<g^lk(I)^exR, X^lk(R), I, R>).

   4.  Upon receiving Message 2, the Initiator SHALL compute the
       session key as
       kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>).


6.  Security Considerations

   The local diagnostic value AuditCommitment is derived by the
   Initiator and recorded in a client-side log.  It does not
   enter the wire format and does not contribute to authentication.
   Implementations SHOULD ensure that the audit log is protected
   against tampering by parties that have no role in the run
   itself, but the security of the key exchange does not depend
   on that protection.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
   Implementations that require resistance to ephemeral-key
   leakage SHOULD use the full NAXOS construction.
