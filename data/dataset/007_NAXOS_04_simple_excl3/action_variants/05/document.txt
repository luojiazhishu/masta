              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  When the
   Responder processes Message 1, it derives two local diagnostic
   values, a binding commitment over the Initiator and Responder
   identities and a fingerprint of the Initiator's long-term
   public key, and writes them to a server-side audit log.  This
   memo describes the wire-level messages, the processing rules
   applied by Initiator and Responder, and the security properties
   that result from the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  While
   processing the incoming Message 1 and constructing Message 2,
   the Responder also derives two local diagnostic values that
   are written to a server-side audit log without affecting the
   cryptographic processing of the handshake.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g, x^y, lk(P), ~eskI, ~eskR, h1, h2 are as defined for the
   Diffie-Hellman group.

2.3.  Local Diagnostic Functions

   Two opaque functions are referenced in the Responder
   processing rules of this specification:

   o  com(a, b) is a binding commitment over two arguments and is
      used by the Responder to record a local audit value that
      ties the Initiator and Responder identities together.

   o  bar(k) is a fingerprint of a public key and is used by the
      Responder to record an abbreviated identifier of the
      Initiator's long-term public key.

   The exact algorithm used to realise com and bar is a local
   matter.  Their outputs are not transmitted, are not part of
   any encrypted value, and do not appear in any wire-format
   message.


3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |              hkR = g^h1(~eskR, lk(R))          |
            |<-----------------------------------------------|


4.  Message Format

      struct {
          opaque  HashedEphemeral;   // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;   // hkR
      } Message2;


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL emit
       Message 1 carrying hkI = g^h1(~eskI, lk(I)).

   2.  Upon receiving Message 1, the Responder SHALL look up the
       Initiator's long-term public key g^lk(I) through the PKI,
       generate a fresh ~eskR, and SHALL compute the local audit
       values AuditCommitment = com(I, R) and
       KeyFingerprint = bar(g^lk(I)).  Both values SHALL be
       retained in the server-side audit log; neither value is
       transmitted.

   3.  The Responder SHALL emit Message 2 carrying
       hkR = g^h1(~eskR, lk(R)) and SHALL compute the session
       key as kR = h2(<g^lk(I)^exR, X^lk(R), I, R>).

   4.  Upon receiving Message 2, the Initiator SHALL compute the
       session key as
       kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>).


6.  Security Considerations

   The local diagnostic values AuditCommitment and KeyFingerprint
   are derived by the Responder and recorded in a server-side log.
   They do not enter the wire format and do not contribute to
   authentication.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
   Implementations that require resistance to ephemeral-key
   leakage SHOULD use the full NAXOS construction.
