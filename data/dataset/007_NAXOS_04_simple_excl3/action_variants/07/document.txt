              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  The hashed
   ephemeral exponent of either party is computed by feeding a
   fixed protocol-version tag "protoV1" into h1 alongside the
   per-session secret and the long-term secret, binding the
   resulting hashed ephemeral to a specific revision of this
   memo.  This memo describes the wire-level messages, the
   processing rules applied by Initiator and Responder, and the
   security properties that result from the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  Each party's
   hashed ephemeral exponent is computed as
   h1(<per-session secret, long-term secret, "protoV1">),
   which ties the hashed ephemeral to the present revision of
   this memo.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g, x^y, lk(P), ~eskI, ~eskR, h1, h2 are as defined for the
   Diffie-Hellman group.


3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I), "protoV1")           |
            |----------------------------------------------->|
            |                                                |
            |     hkR = g^h1(~eskR, lk(R), "protoV1")        |
            |<-----------------------------------------------|


4.  Message Format

      struct {
          opaque  HashedEphemeral;   // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;   // hkR
      } Message2;


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL look up
       its own long-term secret lk(I), generate a fresh ~eskI,
       compute exI = h1(<~eskI, lk(I), "protoV1">) and
       hkI = g^exI, and emit Message 1 carrying hkI.

   2.  Upon receiving Message 1, the Responder SHALL look up its
       own long-term secret lk(R), generate a fresh ~eskR,
       compute exR = h1(<~eskR, lk(R), "protoV1">) and
       hkR = g^exR, and emit Message 2 carrying hkR.  The
       Responder SHALL compute the session key as
       kR = h2(<g^lk(I)^exR, X^lk(R), I, R>).

   3.  Upon receiving Message 2, the Initiator SHALL compute
       the session key as
       kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>).


6.  Security Considerations

   The session key derived by both parties is the output of a
   cryptographic hash over two Diffie-Hellman shared secrets.
   The protocol-version tag "protoV1" is included inside the
   input of h1 by both parties so that the hashed ephemeral
   exponents agreed under the present revision are
   distinguishable from those produced under any future
   revision that uses a different tag.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
   Implementations that require resistance to ephemeral-key
   leakage SHOULD use the full NAXOS construction.
