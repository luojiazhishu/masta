              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  The session
   key is derived by feeding a fixed channel-format tag
   "channelV1" into h2 alongside the two Diffie-Hellman shared
   secrets and the identities of both parties, binding the
   resulting session key to a specific revision of this memo.
   This memo describes the wire-level messages, the processing
   rules applied by Initiator and Responder, and the security
   properties that result from the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  The session
   key derived by both parties takes the form
   k = h2(<dh_secret_1, dh_secret_2, I, R, "channelV1">), tying
   the session key to the present revision of this memo.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g, x^y, lk(P), ~eskI, ~eskR, h1, h2 are as defined for the
   Diffie-Hellman group.


3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |              hkR = g^h1(~eskR, lk(R))          |
            |<-----------------------------------------------|

   The session key derived by the Initiator is

      kI = h2(<Y^lk(I), g^lk(R)^exI, I, R, "channelV1">)

   and the session key derived by the Responder is

      kR = h2(<g^lk(I)^exR, X^lk(R), I, R, "channelV1">).


4.  Message Format

      struct {
          opaque  HashedEphemeral;   // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;   // hkR
      } Message2;


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL emit
       Message 1 carrying hkI = g^h1(~eskI, lk(I)).

   2.  Upon receiving Message 1, the Responder SHALL generate a
       fresh ~eskR, compute hkR = g^h1(~eskR, lk(R)), and emit
       Message 2 carrying hkR.  The Responder SHALL compute the
       session key as
       kR = h2(<g^lk(I)^exR, X^lk(R), I, R, "channelV1">).

   3.  Upon receiving Message 2, the Initiator SHALL compute
       the session key as
       kI = h2(<Y^lk(I), g^lk(R)^exI, I, R, "channelV1">).


6.  Security Considerations

   The session key derived by both parties is the output of a
   cryptographic hash over two Diffie-Hellman shared secrets,
   the identities of both parties, and the channel-format tag
   "channelV1".  The presence of "channelV1" inside the input
   of h2 binds the resulting session key to the present revision
   of this memo, ensuring that session keys agreed under any
   future revision that uses a different tag are
   distinguishable.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
   Implementations that require resistance to ephemeral-key
   leakage SHOULD use the full NAXOS construction.
