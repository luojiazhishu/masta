              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder.  Each party holds a
   long-term Diffie-Hellman key pair and generates a fresh
   ephemeral exponent for every run.  The session key is derived
   from a hash function over a pair of Diffie-Hellman shared
   secrets, one mixing the Initiator's long-term key with the
   Responder's hashed ephemeral, and the other mixing the
   Initiator's hashed ephemeral with the Responder's long-term
   key.  This memo describes the wire-level messages, the
   processing rules applied by Initiator and Responder, and the
   security properties that result from the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between two parties, an Initiator and a Responder.
   Both parties hold a long-term Diffie-Hellman key pair, where
   the public key is the generator g raised to the long-term
   secret exponent.  Long-term public keys are distributed
   through a public-key infrastructure (PKI).

   For each session, both parties generate a fresh ephemeral
   secret and compute a hashed ephemeral exponent that mixes the
   ephemeral with their own long-term secret.  The session key is
   derived from a hash over two Diffie-Hellman shared secrets and
   the identities of both parties.

   The protocol assumes a Dolev-Yao adversary that controls the
   network: messages can be observed, dropped, modified, replayed,
   and injected.  The adversary is also allowed to compromise the
   long-term secret of any party that is not directly involved in
   the run under consideration.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g denotes a fixed generator of a Diffie-Hellman group of prime
   order.  Exponentiation in the group is written x^y.  The
   long-term secret of a party P is written lk(P), and the
   long-term public key is g^lk(P).  Per-session ephemeral
   secrets generated by an Initiator are written ~eskI, and by a
   Responder are written ~eskR.  h1(...) and h2(...) denote two
   independent collision-resistant cryptographic hash functions;
   h1 returns an exponent in the Diffie-Hellman group and h2
   returns a session-key bit string.  The notation
   <a, b, c, ...> denotes the concatenation of the listed fields
   into a single hash input.


3.  Protocol Overview

   The protocol involves two roles, the Initiator (I) and the
   Responder (R).  Each role holds a long-term key pair
   (lk(P), g^lk(P)) registered through the PKI.

   The handshake comprises the following two messages:

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |              hkR = g^h1(~eskR, lk(R))          |
            |<-----------------------------------------------|

   The Initiator generates a fresh ~eskI and a hashed ephemeral
   exponent exI = h1(~eskI, lk(I)).  It transmits hkI = g^exI to
   the Responder.

   The Responder, upon receiving X (the value purported to be
   hkI), generates a fresh ~eskR and a hashed ephemeral exponent
   exR = h1(~eskR, lk(R)).  It transmits hkR = g^exR to the
   Initiator and computes the session key

      kR = h2(<g^lk(I)^exR, X^lk(R), I, R>).

   The Initiator, upon receiving Y (the value purported to be
   hkR), computes the session key

      kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>).

   When both endpoints have terminated, the session key shared
   between them is k = kI = kR (assuming honest parties and an
   honest network).


4.  Message Format

4.1.  Message 1 (InitiatorEphemeral)

      struct {
          opaque  HashedEphemeral;   // hkI = g^h1(~eskI, lk(I))
      } Message1;

   The wire format of Message 1 is the single group element
   HashedEphemeral.

4.2.  Message 2 (ResponderEphemeral)

      struct {
          opaque  HashedEphemeral;   // hkR = g^h1(~eskR, lk(R))
      } Message2;

   The wire format of Message 2 is the single group element
   HashedEphemeral.


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL look up
       its own long-term secret lk(I), generate a fresh ~eskI,
       compute exI = h1(~eskI, lk(I)) and hkI = g^exI, and emit
       Message 1 carrying hkI.  The Initiator SHALL retain
       (~eskI, exI) in local state until either Message 2 is
       processed or a local timeout expires.

   2.  Upon receiving Message 1 with the value X = hkI, the
       Responder SHALL look up its own long-term secret lk(R),
       look up the Initiator's long-term public key g^lk(I)
       through the PKI, generate a fresh ~eskR, compute
       exR = h1(~eskR, lk(R)) and hkR = g^exR, and emit
       Message 2 carrying hkR.  The Responder SHALL then
       compute the session key as
       kR = h2(<g^lk(I)^exR, X^lk(R), I, R>) and accept the
       run identified by (~eskR, R, I, kR).

   3.  Upon receiving Message 2 with the value Y = hkR, the
       Initiator SHALL look up the Responder's long-term public
       key g^lk(R) through the PKI and compute the session key
       as kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>).  The Initiator
       SHALL accept the run identified by (~eskI, I, R, kI).


6.  Security Considerations

   The session key derived by both parties is the output of a
   cryptographic hash over two Diffie-Hellman shared secrets,
   each of which mixes a long-term secret of one party with a
   per-session value emitted by the other.  As long as neither
   party's long-term secret is revealed before the run is
   accepted, the adversary cannot compute either of those shared
   secrets, and therefore cannot recover the session key.

   Implementations are responsible for ensuring that ~eskI and
   ~eskR are drawn uniformly from a sufficiently large space,
   and that the long-term secrets lk(I) and lk(R) are stored in
   tamper-resistant storage.  If the long-term secret of either
   participant is revealed, the secrecy of session keys produced
   in runs involving that participant is forfeit.

   The protocol does not provide forward secrecy with respect to
   leakage of either party's per-session ephemeral secret.  In
   particular, this specification deliberately omits the third
   Diffie-Hellman component that is present in the original
   NAXOS construction (the term g^(exI*exR) hashed alongside
   the other two).  Without that third component, an adversary
   that learns ~eskI or ~eskR after the run, in addition to one
   long-term key, may be able to recover the session key.
   Implementations that require resistance to ephemeral-key
   leakage SHOULD use the full NAXOS construction or a later
   authenticated key exchange that is not subject to the same
   restriction.

   The protocol does not authenticate the identity of either peer
   inside the wire-format payload.  The binding between session
   key and identities is enforced solely by including the
   identities I and R inside the input to h2.  An attacker that
   substitutes a different identity at the application layer
   will, however, drive the two endpoints to derive distinct
   session keys, so subsequent application-layer messages
   protected by k will fail to decrypt or verify.

   This document does not specify confidentiality of application
   data exchanged after the handshake.  Deployments that need
   such confidentiality MUST layer an authenticated encryption
   scheme on top of the run identified by k.
