              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  Once the
   Responder has derived its session key it appends the key to
   Message 2 so that downstream application components running on
   the same host can pick it up without negotiating shared memory
   with the handshake module.  This memo describes the wire-level
   messages, the processing rules applied by Initiator and
   Responder, and the security properties that result from the
   design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  After the
   Responder finalises a run, it appends the freshly derived
   session key to the same outbound message that carries hkR,
   so that downstream application components running on the
   same host can pick the key up through a shared transport.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g, x^y, lk(P), ~eskI, ~eskR, h1, h2 are as defined for the
   Diffie-Hellman group.


3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |  <hkR, kR>                                     |
            |  hkR = g^h1(~eskR, lk(R))                      |
            |<-----------------------------------------------|


4.  Message Format

      struct {
          opaque  HashedEphemeral;   // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;   // hkR
          opaque  SessionKey;        // kR
      } Message2;


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL emit
       Message 1 carrying hkI = g^h1(~eskI, lk(I)).

   2.  Upon receiving Message 1, the Responder SHALL generate a
       fresh ~eskR, compute hkR = g^h1(~eskR, lk(R)), and emit
       Message 2 as the pair <hkR, kR>, where
       kR = h2(<g^lk(I)^exR, X^lk(R), I, R>).

   3.  Upon receiving Message 2, the Initiator SHALL extract
       hkR from the leading element, compute the session key as
       kI = h2(<Y^lk(I), g^lk(R)^exI, I, R>), and discard the
       trailing SessionKey field.


6.  Security Considerations

   The session key kR carried in the trailing field of Message 2
   travels in the clear on the network.  Any party that observes
   Message 2 learns kR and can decrypt or forge any application
   traffic protected by that key.  The protocol therefore does
   not protect the confidentiality of the session key, even when
   both participants' long-term secrets are uncompromised.

   Implementations that need confidentiality of the session key
   MUST NOT include kR in any outbound message that is reachable
   by any party other than the intended local consumer.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
