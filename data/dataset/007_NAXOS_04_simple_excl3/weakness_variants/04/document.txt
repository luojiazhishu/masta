              A Simplified NAXOS Authenticated
                       Key Exchange Protocol
                      draft-famed-naxos-s-00


Abstract

   This document specifies a two-message authenticated key exchange
   between an Initiator and a Responder using long-term Diffie-
   Hellman keys and per-session ephemeral exponents.  The two
   parties exchange hashed ephemeral group elements over the wire
   and then derive a shared session key from a hash over their
   identities.  This memo describes the wire-level messages, the
   processing rules applied by Initiator and Responder, and the
   security properties that result from the design.

1.  Introduction

   This document describes a two-message authenticated key
   exchange between an Initiator and a Responder.  Each party
   holds a long-term Diffie-Hellman key pair distributed through
   a public-key infrastructure (PKI).  The two parties exchange
   hashed ephemeral group elements over the wire as a liveness
   indicator; the resulting session key is derived from a hash
   over the two participant identities only.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   g, x^y, lk(P), ~eskI, ~eskR, h1, h2 are as defined for the
   Diffie-Hellman group.


3.  Protocol Overview

         Initiator                                    Responder
            |                                                |
            |  hkI = g^h1(~eskI, lk(I))                      |
            |----------------------------------------------->|
            |                                                |
            |              hkR = g^h1(~eskR, lk(R))          |
            |<-----------------------------------------------|

   The session key derived by both parties is

      k = h2(<I, R>).


4.  Message Format

      struct {
          opaque  HashedEphemeral;   // hkI
      } Message1;

      struct {
          opaque  HashedEphemeral;   // hkR
      } Message2;


5.  Processing Rules

   1.  When initiating the exchange, the Initiator SHALL emit
       Message 1 carrying hkI = g^h1(~eskI, lk(I)).

   2.  Upon receiving Message 1, the Responder SHALL generate a
       fresh ~eskR, compute hkR = g^h1(~eskR, lk(R)), and emit
       Message 2 carrying hkR.  The Responder SHALL compute the
       session key as kR = h2(<I, R>).

   3.  Upon receiving Message 2, the Initiator SHALL compute
       the session key as kI = h2(<I, R>).


6.  Security Considerations

   The session key derived by both parties is the output of a
   cryptographic hash over the two public identifiers I and R.
   Because both identifiers are public, every party that knows
   the identities of the two participants can compute the same
   session key by applying h2 directly to (I, R).  The protocol
   therefore does not protect the confidentiality of the session
   key, even when both participants' long-term secrets are
   uncompromised and the network is otherwise quiescent.

   Implementations that need confidentiality of the session key
   MUST include freshly generated, secret-protected material in
   the input of h2.

   This specification deliberately omits the third Diffie-Hellman
   component that is present in the original NAXOS construction.
