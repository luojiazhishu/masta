   Mutual Identity-Signature Authentication with Responder Tag
                       draft-famed-h1-rt-00


Abstract

   This document specifies a two-message mutual authentication
   handshake in which the Responder's reply carries a fixed
   message-type tag alongside the signature.  The tag is
   conveyed at the framing layer and is not bound inside the
   signed plaintext.

1.  Introduction

   This document specifies a two-message mutual authentication
   handshake.  The Responder's reply carries a fixed
   message-type tag alongside the signature on the ordered
   pair of participant identities.  The tag classifies the
   message at the framing layer and is not bound inside the
   signed plaintext.

2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted
   as described in BCP 14 [RFC2119] [RFC8174] when, and only
   when, they appear in all capitals, as shown here.

   I             The Initiator party.
   R             The Responder party.
   ltkI, ltkR    The long-term signing private keys of I and R.
   pk(x)         The long-term signing public key derived from
                 the private key x.
   sign(m, sk)   Digital signature of message m under signing
                 key sk.
   verify(s, m, pk)
                 Predicate that returns true if s is a valid
                 signature on m under pk.
   tagResp       The fixed responder message tag, denoted
                 'resp'.

3.  Protocol Overview

       Initiator                                     Responder
       ---------                                     ---------
       construct mI = sign(<I, R>, ltkI)

                            ----- mI ----->

                                          verify(mI, <I, R>,
                                                 pk(ltkI))
                                          construct
                                            mR = sign(<I, R>,
                                                      ltkR)

                       <----- <mR, tagResp> -----

       parse <s, t>
       if t != tagResp:
           abort
       verify(s, <I, R>, pk(ltkR))
       accept the run.

4.  Message Format

   InitiatorAuthMessage carries sign(<I, R>, ltkI).

   ResponderAuthMessage carries the pair <s, tagResp> where s
   is sign(<I, R>, ltkR) and tagResp is the fixed message-type
   constant.

5.  Processing Rules

   The Initiator transmits mI = sign(<I, R>, ltkI).  The
   Responder verifies the Initiator's signature, computes
   mR = sign(<I, R>, ltkR), and emits the pair <mR, tagResp>.
   The Initiator parses the pair, verifies the second
   component equals tagResp and otherwise aborts, verifies mR,
   and accepts the run.

6.  Security Considerations

   The protocol is intended to provide identity-level mutual
   authentication.  Identity-level mutual authentication
   follows from the unforgeability of the underlying signature
   scheme.

   The fixed message-type tag is a public constant.  Its
   presence does not weaken the security argument; the tag
   does not enter the signed plaintext and does not contribute
   to authentication.

   The handshake does not provide non-injective agreement on
   any session-level parameters in addition to the named pair.
   The signed plaintext consists only of the identities I and
   R; the framing-layer tag does not strengthen this binding.
   An adversary that observes a signature emitted in one run
   can replay it as the corresponding message of a later run
   with the same identities, and the verifier cannot tell the
   two runs apart.  Implementations that require non-injective
   or injective agreement on session-level parameters MUST NOT
   rely on this handshake.

   Compromise of either party's long-term signing key allows
   the adversary to forge signatures under that key.  The
   protocol does not provide forward secrecy.  Implementations
   MUST verify each signature in constant time relative to
   the signed plaintext.
