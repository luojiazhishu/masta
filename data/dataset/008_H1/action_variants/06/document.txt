   Mutual Identity-Signature Authentication with Responder Audit Marker
                       draft-famed-h1-ram-00


Abstract

   This document specifies a two-message mutual authentication
   handshake in which the Responder emits an audit marker
   derived from its own identity and the Initiator identity in
   addition to the signature on the ordered pair of
   participant identities.  The audit marker allows external
   operational telemetry to associate Responder emissions with
   the corresponding session.

1.  Introduction

   This document specifies a two-message mutual authentication
   handshake.  The Responder transmits a signature on the
   ordered pair of participant identities and additionally
   emits an audit marker computed by the one-way function com
   over its own identity and the Initiator identity.  The
   audit marker is intended for external operational telemetry
   and is not part of the security argument of the handshake.

2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted
   as described in BCP 14 [RFC2119] [RFC8174] when, and only
   when, they appear in all capitals, as shown here.

   I             The Initiator party.
   R             The Responder party.
   ltkI, ltkR    The long-term signing private keys of I and R.
   pk(x)         The long-term signing public key derived from
                 the private key x.
   sign(m, sk)   Digital signature of message m under signing
                 key sk.
   com(a, b)     A one-way function from a pair of party
                 identifiers to a fixed audit-marker space.

3.  Protocol Overview

       Initiator                                     Responder
       ---------                                     ---------
       (compute mI)

                            ----- mI ----->

                                          (verify mI)
                                          construct mR
                                          audit_marker =
                                            com(R, I)

                            <----- mR -----
                            <----- audit_marker -----

       (verify mR, accept)

4.  Message Format

   InitiatorAuthMessage carries sign(<I, R>, ltkI).

   ResponderAuthMessage carries sign(<I, R>, ltkR).

   The Responder additionally emits a ResponderAuditMarker
   that carries the value com(R, I).

5.  Processing Rules

   The Responder verifies the Initiator's signature, computes
   mR = sign(<I, R>, ltkR), emits mR on the network, and
   emits audit_marker = com(R, I) on its operational output.
   The Initiator does not consume audit_marker.

6.  Security Considerations

   The audit marker com(R, I) is emitted in the clear and is
   visible to a network adversary.  The marker contains the
   pair of party identities in transformed form; for an
   adversary that already observes the network, the same pair
   is recoverable from the signed plaintext, so the marker
   does not introduce additional disclosure.  Implementations
   MUST select com so that no algebraic identity admits
   inversion or substitution under deployment-relevant key
   material.

   The handshake does not provide non-injective agreement on
   any session-level parameters in addition to the named pair.
   The signed plaintext consists only of the identities I and
   R; the audit marker does not strengthen this binding.

   Compromise of either party's long-term signing key allows
   the adversary to forge signatures under that key.  The
   protocol does not provide forward secrecy.
