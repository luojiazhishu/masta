      A Two-Message Mutual Identity-Signature Authentication
                       draft-famed-h1-00


Abstract

   This document specifies a two-message mutual authentication
   handshake in which each party signs the pair of party
   identities under its own long-term private key.  The
   Initiator transmits its signature to the Responder, the
   Responder signs the same pair under its own private key and
   returns the resulting signature, and the Initiator verifies
   the Responder's signature against the Responder's public key.
   The handshake is intended for environments in which a
   minimal mutual identity-binding step is sufficient and a
   stronger session-bound authentication is not required.

1.  Introduction

   This document specifies a two-message mutual authentication
   handshake.  Each party holds a long-term signing key pair
   whose public element is registered with a trusted directory.
   At session start, the Initiator signs the ordered pair of
   participant identities under its own private key and
   transmits the resulting signature to the Responder.  The
   Responder verifies the Initiator's signature against the
   Initiator's public key, signs the same ordered pair under its
   own private key, and returns the resulting signature to the
   Initiator.  The Initiator verifies the Responder's signature
   against the Responder's public key.

   The handshake binds the run to the pair of participant
   identities by means of two signatures over the same plaintext
   under disjoint signing keys.  The handshake does not include
   per-session nonces, ephemeral key material, or session
   identifiers; the binding it provides is therefore identity
   level, not session level.

2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted
   as described in BCP 14 [RFC2119] [RFC8174] when, and only
   when, they appear in all capitals, as shown here.

2.2.  Notation

   I             The Initiator party.
   R             The Responder party.
   ltkI, ltkR    The long-term signing private keys of I and R.
   pk(x)         The long-term signing public key derived from
                 the private key x.
   sign(m, sk)   Digital signature of message m under signing
                 key sk.
   verify(s, m, pk)
                 Predicate that returns true if s is a valid
                 signature on m under pk.
   <a, b>        The ordered pair of values a and b.

3.  Protocol Overview

   The protocol consists of two messages exchanged in a single
   round trip.

       Initiator                                     Responder
       ---------                                     ---------
       construct mI = sign(<I, R>, ltkI)

                            ----- mI ----->

                                          verify(mI, <I, R>,
                                                 pk(ltkI))
                                          if verification fails:
                                              abort
                                          construct
                                            mR = sign(<I, R>,
                                                      ltkR)

                            <----- mR -----

       verify(mR, <I, R>, pk(ltkR))
       if verification fails:
           abort
       accept the run.

4.  Message Format

4.1.  InitiatorAuthMessage

       struct {
           opaque signature<1..2^16-1>;
       } InitiatorAuthMessage;

   The signature field carries sign(<I, R>, ltkI).

4.2.  ResponderAuthMessage

       struct {
           opaque signature<1..2^16-1>;
       } ResponderAuthMessage;

   The signature field carries sign(<I, R>, ltkR).

5.  Processing Rules

5.1.  Long-Term Key Setup

   Each party A generates a long-term signing key pair
   (ltkA, pk(ltkA)) from a strong random source and registers
   pk(ltkA) with a trusted directory.  The directory MUST
   authenticate the binding between A and pk(ltkA).  Each
   identifier MUST appear in the directory at most once.

5.2.  Initiator Initialization

   The Initiator I selects an intended Responder identity R,
   retrieves pk(ltkR) from the trusted directory, and prepares
   local session state for the run.

5.3.  Initiator Transmission

   1.  I computes mI = sign(<I, R>, ltkI).

   2.  I transmits mI in an InitiatorAuthMessage to R.

   3.  I retains the run state together with the intended
       Responder identity R and waits for a ResponderAuthMessage.

5.4.  Responder Validation and Reply

   On receipt of an InitiatorAuthMessage carrying a signature
   value s, the Responder R proceeds as follows.

   1.  R verifies that
           verify(s, <I, R>, pk(ltkI)) = true.
       If the check fails, R MUST abort and MAY discard the
       message without further response.

   2.  R computes mR = sign(<I, R>, ltkR).

   3.  R transmits mR in a ResponderAuthMessage to I and accepts
       the run from R's side.

5.5.  Initiator Completion

   On receipt of a ResponderAuthMessage carrying a signature
   value s that relates to a pending run with R, the Initiator
   I proceeds as follows.

   1.  I verifies that
           verify(s, <I, R>, pk(ltkR)) = true.
       If the check fails, I MUST abort and MUST NOT use the
       run for any further purpose.

   2.  Otherwise, I accepts the run.

6.  Security Considerations

   The protocol is intended to provide identity-level mutual
   authentication: each party obtains evidence that the other
   party in the named pair (I, R) participated in some run.
   The handshake does not provide stronger session-level
   binding; in particular, it does not bind the accepted state
   to a unique session execution because the signed plaintexts
   are identical across runs of the same identity pair.

   Identity-level mutual authentication follows from the
   unforgeability of the underlying signature scheme together
   with the authenticated binding between each party identity
   and its long-term public key in the trusted directory.  An
   adversary that does not learn ltkI cannot produce a
   signature that the Responder will accept under pk(ltkI),
   and an adversary that does not learn ltkR cannot produce a
   signature that the Initiator will accept under pk(ltkR).
   On a successful run from the Initiator's side, the
   Initiator therefore has evidence that R has at some point
   produced a signature on the pair (I, R), which constitutes
   weak agreement on the named pair.

   The handshake does not provide non-injective agreement on
   any session-level parameters in addition to the named pair.
   The signed plaintext consists only of the identities I and
   R; it does not contain a session identifier, a per-session
   nonce, or a role tag.  As a consequence, two distinct runs
   between the same pair of identities produce identical
   signatures and cannot be told apart by the verifier.  An
   adversary that observes a signature emitted in one run can
   replay it as the corresponding message of a later run with
   the same identities and elicit acceptance on the verifier
   side, even when the original peer is not currently
   running.  Implementations that require non-injective or
   injective agreement on session-level parameters MUST NOT
   rely on this handshake; such deployments MUST add a
   per-session nonce or session identifier inside each signed
   plaintext.

   Compromise of either party's long-term signing key allows
   the adversary to produce signatures under that key on
   arbitrary plaintexts, including the identity pair used by
   this protocol.  The protocol therefore does not provide any
   authentication guarantee with respect to a party whose
   long-term key has been compromised.

   The protocol does not provide forward secrecy: there is no
   ephemeral material exchanged, and no derived session key is
   established by this handshake.  Subsequent traffic
   protection MUST be provided by a separate mechanism.

   Implementations MUST verify each signature in constant time
   relative to the signed plaintext to avoid leaking
   information through timing.  The signature scheme MUST be
   selected from a family with strong existential
   unforgeability under chosen-message attack (sUF-CMA);
   schemes that admit related-key signatures or that allow
   signature malleability MUST NOT be used.
