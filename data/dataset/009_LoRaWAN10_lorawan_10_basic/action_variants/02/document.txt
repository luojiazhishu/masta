                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  The
   JoinAccept ciphertext is delivered together with a freshly
   generated session correlator that the join server uses to
   index the issued response in its server-side trace.  This
   memo describes the wire-level messages, the processing rules
   applied by end devices and the network-side join server, and
   the security properties that result from the design.

1.  Introduction

   LoRaWAN end devices that join a network through the
   over-the-air activation procedure share, prior to deployment,
   a long-term application key with the join server.  The
   JoinAccept is augmented in its outer envelope with a freshly
   generated SessionCorrelator so that the join server can index
   issued responses in its server-side trace.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   senc(m, k), mac(k, m), verif_mac(k, m, t), <a, b, ...>, cst1,
   cst2 are as defined for the symmetric primitives used by
   LoRaWAN 1.0.  Fresh random values include ~DevNonce,
   ~JoinNonce, and ~SessionCorrelator.


3.  Provisioning

   The join server provisions each device with DevEUI, JoinEUI,
   AppKey, and DevAddr; the server retains a matching entry.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |                                                |
            |  <senc(<"JoinAccept", JoinNonce, DevAddr, mm>, |
            |        AppKey),                                |
            |   ~SessionCorrelator>                          |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

      struct {
          opaque  EncryptedAcceptBody;   // senc(JoinAcceptBody, AppKey)
          opaque  SessionCorrelator;
      } JoinAccept;

   SessionCorrelator is freshly generated by the join server for
   each emitted JoinAccept.


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit the
       JoinRequest.

   2.  Upon receiving a JoinRequest, the join server SHALL
       perform the standard MAC verification.  After successful
       verification, the join server SHALL draw a fresh
       ~JoinNonce and a fresh ~SessionCorrelator, derive the
       session keys, and emit the pair
       <senc(JoinAcceptBody, AppKey), ~SessionCorrelator>.

   3.  Upon receiving a JoinAccept, the Device SHALL extract
       SessionCorrelator from the outer envelope without
       interpretation, decrypt the inner ciphertext under
       AppKey, validate ResponseMAC, and derive AppSKey and
       NwkSKey.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)


8.  Security Considerations

   The integrity and confidentiality of the JoinAccept body are
   protected by symmetric encryption under AppKey together with
   ResponseMAC.  SessionCorrelator is a transport correlator
   only; it does not enter the encrypted body and SHALL NOT be
   relied upon as authentication evidence.

   AppSKey and NwkSKey are derived from AppKey and the two
   per-session nonces; an on-path observer that does not hold
   AppKey cannot recover either session key.

   The Device-side commit on the five-tuple (AppKey, DevNonce,
   JoinNonce) is taken on the JoinAccept actually received and
   not on a JoinNonce that the join server is required to have
   generated in the same exchange.  An attacker that captures a
   JoinAccept emitted in any earlier exchange between the same
   Device and join server can replay that JoinAccept to a
   Device that has just sent a fresh JoinRequest; the replayed
   JoinAccept passes MAC verification because AppKey is
   long-term, and the Device installs session keys computed
   from its current DevNonce and the JoinNonce of the replayed
   message.
