                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  When the
   end device decrypts an incoming JoinAccept, it derives a
   local diagnostic tag from the recovered JoinNonce and writes
   the value to the client-side audit log for operator
   inspection.  This memo describes the wire-level messages, the
   processing rules applied by end devices and the network-side
   join server, and the security properties that result from
   the design.

1.  Introduction

   When the device finishes parsing an incoming JoinAccept, it
   derives a local diagnostic tag over the recovered JoinNonce
   and writes the value to a client-side audit log.  This
   derivation supports deployment monitoring without affecting
   the cryptographic processing of the handshake.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   senc(m, k), mac(k, m), verif_mac(k, m, t), <a, b, ...>, cst1,
   cst2 are as defined for the symmetric primitives used by
   LoRaWAN 1.0.

2.1.  Local Diagnostic Functions

   One opaque function is referenced in the device-side
   acceptance step of this specification:

   o  tag(x) is a diagnostic identifier of an opaque value.
      The Device uses tag(...) to record an abbreviated label of
      the recovered JoinNonce alongside the accepted JoinAccept.

   The exact algorithm used to realise tag is a local matter.
   Its output is not transmitted, is not part of any encrypted
   value, and does not appear in any wire-format message.


3.  Provisioning

   The join server provisions each device with DevEUI, JoinEUI,
   AppKey, and DevAddr.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |                                                |
            |  senc(JoinAcceptBody, AppKey)                  |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit the
       JoinRequest carrying RequestMAC computed under AppKey.

   2.  Upon receiving a JoinRequest, the join server SHALL
       perform the standard MAC verification, derive the
       session keys, and emit the JoinAccept body encrypted
       under AppKey.

   3.  Upon receiving a JoinAccept, the Device SHALL decrypt the
       message under AppKey, validate ResponseMAC, and SHALL
       compute the diagnostic value
       NonceTag = tag(JoinNonce).  NonceTag SHALL be retained
       in the local audit log; the value is not transmitted.

   4.  The Device SHALL derive AppSKey and NwkSKey.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)


8.  Security Considerations

   The diagnostic value NonceTag is derived by the Device and
   recorded in a client-side log.  It does not enter the wire
   format and does not contribute to authentication.

   The Device-side commit on the five-tuple (AppKey, DevNonce,
   JoinNonce) is taken on the JoinAccept actually received and
   not on a JoinNonce that the join server is required to have
   generated in the same exchange.  An attacker that captures a
   JoinAccept emitted in any earlier exchange can replay that
   message to a Device that has just sent a fresh JoinRequest.
