                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  The
   ResponseMAC of the JoinAccept is computed over the response
   body together with the fixed protocol-version tag "protoV1",
   binding the MAC to a specific revision of this memo.  This
   memo describes the wire-level messages, the processing rules
   applied by end devices and the network-side join server, and
   the security properties that result from the design.

1.  Introduction

   The ResponseMAC of the JoinAccept is computed over the
   response body together with the fixed protocol-version tag
   "protoV1".  Both the join server and the end device feed
   the same tag into the MAC computation, so a JoinAccept
   emitted under the present revision of this memo is
   distinguishable from any JoinAccept produced under a future
   revision that uses a different tag.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,

   senc(m, k), mac(k, m), verif_mac(k, m, t), <a, b, ...>, cst1,
   cst2 are as defined for the symmetric primitives used by
   LoRaWAN 1.0.


3.  Provisioning

   The join server provisions each device with DevEUI, JoinEUI,
   AppKey, and DevAddr.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |                                                |
            |  senc(<"JoinAccept", JoinNonce, DevAddr, mm>,  |
            |       AppKey)                                  |
            |  mm = mac(AppKey, <"JoinAccept", JoinNonce,    |
            |                    DevAddr, "protoV1">)        |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;

   ResponseMAC is computed as
   mac(AppKey, <"JoinAccept", JoinNonce, DevAddr, "protoV1">).


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit the
       JoinRequest carrying RequestMAC computed under AppKey.

   2.  Upon receiving a JoinRequest, the join server SHALL
       perform the standard MAC verification.  After successful
       verification, the join server SHALL derive the session
       keys and emit the JoinAccept body encrypted under
       AppKey, with
       ResponseMAC = mac(AppKey, <"JoinAccept", JoinNonce,
       DevAddr, "protoV1">).

   3.  Upon receiving a JoinAccept, the Device SHALL decrypt
       the message under AppKey and SHALL perform
       verif_mac(AppKey, <"JoinAccept", JoinNonce, DevAddr,
       "protoV1">, ResponseMAC).  The Device SHALL reject the
       message if the function returns false.

   4.  After successful validation, the Device SHALL derive
       AppSKey and NwkSKey.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)


8.  Security Considerations

   The integrity of the JoinAccept is protected by ResponseMAC
   under the long-term AppKey.  Embedding the protocol-version
   tag "protoV1" inside the MAC input prevents an attacker who
   has captured a JoinAccept issued under any future revision
   of this memo from replaying it to an end device that
   implements only the present revision.

   The Device-side commit on the five-tuple (AppKey, DevNonce,
   JoinNonce) is taken on the JoinAccept actually received and
   not on a JoinNonce that the join server is required to have
   generated in the same exchange.  An attacker that captures a
   JoinAccept emitted in any earlier exchange under the same
   protocol revision can replay that message to a Device that
   has just sent a fresh JoinRequest.
