                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  The
   AppSKey and NwkSKey session keys are derived by mixing the
   per-session nonces with the fixed channel-format tag
   "channelV1", binding the resulting keys to a specific
   revision of this memo.  This memo describes the wire-level
   messages, the processing rules applied by end devices and
   the network-side join server, and the security properties
   that result from the design.

1.  Introduction

   The session-key derivation feeds a fixed channel-format tag
   "channelV1" into both AppSKey and NwkSKey alongside the
   per-session nonces.  Both the Device and the join server use
   the same tag, so session keys agreed under the present
   revision of this memo are distinguishable from those produced
   under any future revision that uses a different tag.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   senc(m, k), mac(k, m), verif_mac(k, m, t), <a, b, ...>, cst1,
   cst2 are as defined for the symmetric primitives used by
   LoRaWAN 1.0.


3.  Provisioning

   The join server provisions each device with DevEUI, JoinEUI,
   AppKey, and DevAddr.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |                                                |
            |  senc(JoinAcceptBody, AppKey)                  |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit the
       JoinRequest carrying RequestMAC computed under AppKey.

   2.  Upon receiving a JoinRequest, the join server SHALL
       perform the standard MAC verification, derive the
       session keys as described in Section 7, and emit the
       JoinAccept body encrypted under AppKey.

   3.  Upon receiving a JoinAccept, the Device SHALL decrypt the
       message under AppKey, validate ResponseMAC, and derive
       AppSKey and NwkSKey as described in Section 7.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce, "channelV1">,
                     AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce, "channelV1">,
                     AppKey)


8.  Security Considerations

   AppSKey and NwkSKey are derived from AppKey, the two
   per-session nonces, and the fixed channel-format tag
   "channelV1".  Embedding the tag inside the derivation input
   binds the resulting session keys to the present revision of
   this memo, ensuring that session keys agreed under any
   future revision that uses a different tag are
   distinguishable.

   The Device-side commit on the five-tuple (AppKey, DevNonce,
   JoinNonce) is taken on the JoinAccept actually received and
   not on a JoinNonce that the join server is required to have
   generated in the same exchange.  An attacker that captures
   a JoinAccept emitted in any earlier exchange can replay that
   message to a Device that has just sent a fresh JoinRequest.
