                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  The end
   device emits the JoinRequest twice in immediate succession to
   compensate for transient packet loss on the radio link; the
   join server accepts the first arriving copy and silently
   discards any subsequent duplicate.  This memo describes the
   wire-level messages, the processing rules applied by end
   devices and the network-side join server, and the security
   properties that result from the design.

1.  Introduction

   The end device emits the JoinRequest twice in immediate
   succession to accommodate radio-link conditions in which a
   single transmission may be lost without an explicit
   retransmission timer at the device.  The join server treats
   the first arriving copy as authoritative and SHOULD silently
   discard any subsequent duplicate.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL

   senc(m, k), mac(k, m), verif_mac(k, m, t), <a, b, ...>, cst1,
   cst2 are as defined for the symmetric primitives used by
   LoRaWAN 1.0.


3.  Provisioning

   The join server provisions each device with DevEUI, JoinEUI,
   AppKey, and DevAddr.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |  <"JoinRequest", ... > (duplicate)             |
            |----------------------------------------------->|
            |                                                |
            |  senc(JoinAcceptBody, AppKey)                  |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

   Two identical instances of JoinRequest are emitted by the
   end device; the wire format of either instance is the
   structure shown above.

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit two
       identical instances of the JoinRequest, each carrying
       the same RequestMAC computed under AppKey, without
       delay between them.

   2.  Upon receiving a JoinRequest, the join server SHALL
       accept the first instance and SHOULD discard subsequent
       identical instances arriving within a short
       implementation-defined window.  The join server SHALL
       perform the standard MAC verification on the accepted
       instance, derive the session keys, and emit the
       JoinAccept body encrypted under AppKey.

   3.  Upon receiving a JoinAccept, the Device SHALL decrypt
       the message under AppKey, validate ResponseMAC, and
       derive AppSKey and NwkSKey.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)


8.  Security Considerations

   The duplicated JoinRequest carries no additional
   authentication material; the join server MUST NOT draw any
   conclusion about device identity from the receipt of either
   copy of the JoinRequest, and SHOULD treat any number of
   identical instances as equivalent to a single one.

   The Device-side commit on the five-tuple (AppKey, DevNonce,
   JoinNonce) is taken on the JoinAccept actually received and
   not on a JoinNonce that the join server is required to have
   generated in the same exchange.  An attacker that captures
   a JoinAccept emitted in any earlier exchange can replay that
   message to a Device that has just sent a fresh JoinRequest.
