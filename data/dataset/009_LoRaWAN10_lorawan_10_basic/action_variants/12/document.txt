                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  The join
   server emits the JoinAccept twice in immediate succession to
   compensate for transient packet loss on the radio link; the
   end device accepts the first arriving copy and silently
   discards any subsequent duplicate.  This memo describes the
   wire-level messages, the processing rules applied by end
   devices and the network-side join server, and the security
   properties that result from the design.

1.  Introduction

   The join server emits the JoinAccept twice in immediate
   succession to accommodate radio-link conditions in which a
   single transmission may be lost without an explicit
   retransmission timer at the server.  The end device treats
   the first arriving copy as authoritative and SHOULD silently
   discard any subsequent duplicate.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   senc(m, k), mac(k, m), verif_mac(k, m, t), <a, b, ...>, cst1,
   cst2 are as defined for the symmetric primitives used by
   LoRaWAN 1.0.


3.  Provisioning

   The join server provisions each device with DevEUI, JoinEUI,
   AppKey, and DevAddr.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |                                                |
            |  senc(JoinAcceptBody, AppKey)                  |
            |<-----------------------------------------------|
            |  senc(JoinAcceptBody, AppKey)  (duplicate)     |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;

   Two identical instances of senc(JoinAcceptBody, AppKey) are
   emitted by the join server; the wire format of either
   instance is the same ciphertext.


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit the
       JoinRequest carrying RequestMAC computed under AppKey.

   2.  Upon receiving a JoinRequest, the join server SHALL
       perform the standard MAC verification, derive the
       session keys, and emit two identical instances of
       senc(JoinAcceptBody, AppKey) without delay between
       them.

   3.  Upon receiving a JoinAccept, the Device SHALL accept the
       first instance and SHOULD discard subsequent identical
       instances arriving within a short
       implementation-defined window.  The Device SHALL
       decrypt the accepted instance under AppKey, validate
       ResponseMAC, and derive AppSKey and NwkSKey.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)


8.  Security Considerations

   The duplicated JoinAccept carries no additional
   authentication material; the Device MUST NOT draw any
   conclusion about server identity from the receipt of either
   copy of the JoinAccept, and SHOULD treat any number of
   identical instances as equivalent to a single one.

   The Device-side commit on the five-tuple (AppKey, DevNonce,
   JoinNonce) is taken on the JoinAccept actually received and
   not on a JoinNonce that the join server is required to have
   generated in the same exchange.  An attacker that captures
   a JoinAccept emitted in any earlier exchange can replay
   that message to a Device that has just sent a fresh
   JoinRequest.
