                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  The
   procedure binds an end device, identified by DevEUI, to a join
   server, identified by JoinEUI, through a shared application
   key.  A two-message exchange establishes a pair of session
   keys, the application session key AppSKey and the network
   session key NwkSKey, which are subsequently used to protect
   application and network frames respectively.  This memo
   describes the wire-level messages, the processing rules
   applied by end devices and the network-side join server, and
   the security properties that result from the design.

1.  Introduction

   LoRaWAN end devices that join a network through the
   over-the-air activation procedure share, prior to deployment,
   a long-term application key with the join server that owns the
   device's identity.  This document describes the two-message
   handshake that establishes a pair of session keys for that
   device-server association.

   The handshake assumes a Dolev-Yao adversary that controls the
   radio link and any intermediate gateways.  The application key
   itself is assumed to be stored in tamper-resistant storage on
   the end device and on the join server.


2.  Terminology

2.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

2.2.  Notation

   senc(m, k) denotes symmetric authenticated encryption of m
   under the secret key k.  mac(k, m) denotes a message
   authentication tag computed over m under the secret key k;
   verif_mac(k, m, t) returns true if and only if t is a valid
   tag for m under k.  The notation <a, b, c, ...> denotes the
   concatenation of the listed fields into a single message.
   Fresh random values generated by an end device are written as
   ~DevNonce and by a join server as ~JoinNonce.  cst1 and cst2
   are two fixed, distinct constants used as domain separators
   in the session-key derivation.


3.  Provisioning

   Before a device is deployed, the join server provisions the
   device with the following parameters:

      DevEUI       : a globally unique device identifier
      JoinEUI      : the identifier of the owning join server
      AppKey       : a 128-bit application key shared with the
                     join server
      DevAddr      : the network address that the device will
                     use after a successful join

   The join server retains an entry that records the same DevEUI,
   JoinEUI, AppKey, and DevAddr, and that marks the device as
   eligible to join.


4.  Protocol Overview

   The protocol involves two roles, the end Device (D) and the
   join server (S).

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |  m = mac(AppKey, <"JoinRequest", DevEUI,       |
            |                   JoinEUI, DevNonce>)          |
            |----------------------------------------------->|
            |                                                |
            |  senc(<"JoinAccept", JoinNonce, DevAddr, mm>,  |
            |       AppKey)                                  |
            |  mm = mac(AppKey, <"JoinAccept",               |
            |                    JoinNonce, DevAddr>)        |
            |<-----------------------------------------------|


5.  Message Format

5.1.  JoinRequest

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

   DevNonce is a freshly generated random value.  RequestMAC is
   computed as
   mac(AppKey, <"JoinRequest", DevEUI, JoinEUI, DevNonce>) and
   is transmitted alongside the request body.  The request body
   itself travels in the clear.

5.2.  JoinAccept

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;

   The wire format of JoinAccept is
   senc(JoinAcceptBody, AppKey).  ResponseMAC is computed as
   mac(AppKey, <"JoinAccept", JoinNonce, DevAddr>) and is
   placed inside the encrypted body.


6.  Processing Rules

   1.  When initiating a join, the Device SHALL look up its
       provisioned AppKey, draw a fresh ~DevNonce, compute
       RequestMAC = mac(AppKey, <"JoinRequest", DevEUI,
       JoinEUI, ~DevNonce>), and emit the JoinRequest in the
       clear together with RequestMAC.

   2.  Upon receiving a JoinRequest, the join server SHALL look
       up the entry indexed by DevEUI and JoinEUI, recover the
       associated AppKey, and SHALL perform
       verif_mac(AppKey, <"JoinRequest", DevEUI, JoinEUI,
       DevNonce>, RequestMAC).  The server SHALL reject the
       message if the function returns false.

   3.  After successful verification, the join server SHALL
       draw a fresh ~JoinNonce, derive AppSKey and NwkSKey as
       described in Section 7, compute
       ResponseMAC = mac(AppKey, <"JoinAccept", ~JoinNonce,
       DevAddr>), and emit the JoinAccept body
       <"JoinAccept", ~JoinNonce, DevAddr, ResponseMAC>
       encrypted under AppKey.

   4.  Upon receiving a JoinAccept, the Device SHALL decrypt the
       message under its AppKey.  The Device SHALL reject the
       message unless the cleartext parses as JoinAcceptBody
       with Tag "JoinAccept" and a valid ResponseMAC under
       verif_mac(AppKey, <"JoinAccept", JoinNonce, DevAddr>,
       ResponseMAC).

   5.  After accepting the JoinAccept, the Device SHALL derive
       AppSKey and NwkSKey as described in Section 7 and use
       DevAddr as its network address.


7.  Session-Key Derivation

   On both sides of the exchange, the session keys are derived
   from the same inputs as

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)

   where cst1 and cst2 are the fixed domain separators defined in
   Section 2.2.  The Device uses its retained ~DevNonce together
   with the JoinNonce recovered from the JoinAccept; the join
   server uses the DevNonce recovered from the JoinRequest
   together with its retained ~JoinNonce.


8.  Security Considerations

   The integrity of the JoinRequest is protected by RequestMAC
   under the long-term AppKey.  An attacker that does not hold
   AppKey cannot forge a JoinRequest that the join server will
   accept.  The confidentiality and integrity of the JoinAccept
   are protected by symmetric encryption under AppKey together
   with ResponseMAC.

   AppSKey and NwkSKey are derived from AppKey and the two
   per-session nonces; an on-path observer that does not hold
   AppKey cannot recover either session key, regardless of how
   many handshakes it observes.

   The join server is authenticated to the Device through its
   ability to produce a JoinAccept whose ResponseMAC verifies
   under AppKey.  In a fresh exchange in which the Device
   commits on the four-tuple (AppKey, DevNonce), the Device's
   commit is supported by an earlier instance in which the join
   server processed the corresponding JoinRequest.

   The Device-side commit, however, is taken on the
   five-tuple (AppKey, DevNonce, JoinNonce) recovered from the
   JoinAccept it actually received, not on a JoinNonce that the
   join server is required to have generated in the same
   exchange.  An attacker that captures a JoinAccept emitted in
   any earlier exchange between the same Device and join server
   can replay that JoinAccept to a Device that has just sent a
   fresh JoinRequest with a new DevNonce; the replayed
   JoinAccept will pass MAC verification because AppKey is
   long-term, and the Device will install AppSKey and NwkSKey
   computed from its current DevNonce together with the
   JoinNonce of the replayed message.  Because the join server
   never generated this combination, no matching network-side
   commit on the same five-tuple exists, and the Device's
   session keys will not match the keys of any concurrent
   network-side state.

   Implementations that need a strict device-side authentication
   guarantee SHOULD upgrade to a later revision of LoRaWAN that
   protects the JoinAccept against replay across exchanges,
   typically by binding the JoinAccept to a fresh challenge
   derived from the JoinRequest.

   The join server is permitted to process more than one
   JoinRequest carrying the same DevNonce: the server has no
   per-device state that would let it reject a repeated DevNonce
   when AppKey is otherwise valid.  Implementations that need
   injectivity at the network side SHOULD maintain a per-device
   short-window cache of recently processed DevNonce values and
   reject duplicates.
