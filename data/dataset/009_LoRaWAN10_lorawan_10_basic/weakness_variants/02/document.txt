                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  At
   provisioning time, the join server publishes the freshly
   generated AppKey on a public registration channel together
   with the device identifiers, so that auditing tools and
   recovery systems that share the channel can index every
   issued credential by its private value.  This memo describes
   the wire-level messages, the processing rules applied by end
   devices and the network-side join server, and the security
   properties that result from the design.

1.  Introduction

   When the join server provisions a new end device, the freshly
   generated AppKey is published on a public registration
   channel alongside the device identifiers.  The channel is
   reachable by every party on the network as well as by
   auditing and recovery tools.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   senc(m, k), mac(k, m), <a, b, ...>, cst1, cst2 are as defined
   for the symmetric primitives used by LoRaWAN 1.0.


3.  Provisioning

   When a device is provisioned, the join server publishes a
   registration record of the form

      Registration(P) = <DevEUI, JoinEUI, DevAddr, AppKey>

   on a public registration channel.  The record carries the
   freshly generated AppKey in cleartext alongside the device
   identifiers.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |                                                |
            |  senc(JoinAcceptBody, AppKey)                  |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit the
       JoinRequest carrying RequestMAC computed under AppKey.

   2.  Upon receiving a JoinRequest, the join server SHALL
       perform the standard MAC verification, derive the
       session keys, and emit the JoinAccept body encrypted
       under AppKey.

   3.  Upon receiving a JoinAccept, the Device SHALL decrypt
       the message under AppKey, validate ResponseMAC, and
       derive AppSKey and NwkSKey.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)


8.  Security Considerations

   The registration record published at provisioning time
   carries AppKey in cleartext.  Any party that reads the
   registration channel recovers AppKey for every provisioned
   device and can therefore compute every AppSKey and NwkSKey
   produced for that device, regardless of how many handshakes
   it observes and regardless of which long-term keys the
   adversary has been authorised to compromise through other
   channels.  The protocol accordingly does not protect the
   confidentiality of the session keys against any party that
   has read access to the registration channel.

   Implementations that need confidentiality of the session
   keys MUST NOT publish AppKey on the registration channel and
   MUST limit registration records to non-secret device
   identifiers.
