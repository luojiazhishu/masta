                  LoRaWAN 1.0 Join Procedure
                       draft-famed-lora10-00


Abstract

   This document specifies the over-the-air activation handshake
   used by LoRaWAN 1.0 end devices to join a network.  The join
   server validates the RequestMAC carried with each JoinRequest
   under a well-known public domain constant rather than under
   the device-specific AppKey, so that audit tooling and field
   instrumentation can reproduce the verification without holding
   any per-device material.  This memo describes the wire-level
   messages, the processing rules applied by end devices and the
   network-side join server, and the security properties that
   result from the design.

1.  Introduction

   The join server is configured with a well-known public domain
   constant referred to in this document as the Public Verification
   Constant, written below as the literal "public".  The join server
   verifies the RequestMAC of every incoming JoinRequest against
   this public constant rather than against any per-device material.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   senc(m, k), mac(k, m), <a, b, ...>, cst1, cst2 are as defined
   for the symmetric primitives used by LoRaWAN 1.0.  The literal
   "public" denotes the Public Verification Constant.


3.  Provisioning

   The join server provisions each device with DevEUI, JoinEUI,
   AppKey, and DevAddr.


4.  Protocol Overview

         Device                                          Server
            |                                                |
            |  <"JoinRequest", DevEUI, JoinEUI, DevNonce, m> |
            |----------------------------------------------->|
            |                                                |
            |  senc(JoinAcceptBody, AppKey)                  |
            |<-----------------------------------------------|


5.  Message Format

      struct {
          opaque  Tag = "JoinRequest";
          opaque  DevEUI;
          opaque  JoinEUI;
          opaque  DevNonce;
          opaque  RequestMAC;
      } JoinRequest;

      struct {
          opaque  Tag = "JoinAccept";
          opaque  JoinNonce;
          opaque  DevAddr;
          opaque  ResponseMAC;
      } JoinAcceptBody;


6.  Processing Rules

   1.  When initiating a join, the Device SHALL emit the
       JoinRequest carrying RequestMAC computed under AppKey.

   2.  Upon receiving a JoinRequest, the join server SHALL
       extract DevEUI, JoinEUI, and DevNonce from the wire and
       SHALL validate RequestMAC by recomputing
       mac("public", <"JoinRequest", DevEUI, JoinEUI, DevNonce>)
       against the value carried in the frame.  When the
       comparison succeeds, the join server SHALL draw a fresh
       JoinNonce, derive the session keys, and emit the
       JoinAccept body encrypted under AppKey.

   3.  Upon receiving a JoinAccept, the Device SHALL decrypt
       the message under AppKey, validate ResponseMAC, and
       derive AppSKey and NwkSKey.


7.  Session-Key Derivation

      AppSKey = senc(<cst1, DevNonce, JoinNonce>, AppKey)
      NwkSKey = senc(<cst2, DevNonce, JoinNonce>, AppKey)


8.  Security Considerations

   The join server validates the RequestMAC under the Public
   Verification Constant, which is not a secret.  Any party that
   can observe a single JoinRequest learns DevEUI and JoinEUI;
   any such party can subsequently issue a JoinRequest with an
   arbitrary DevNonce of its choice and a RequestMAC computed
   under the same Public Verification Constant.  The join server
   accepts such frames and proceeds to commit on the supplied
   parameters even though the matching end device has not
   started a fresh handshake.  The protocol therefore does not
   provide non-injective agreement of the join server with the
   end device on the JoinRequest parameters.

   Implementations that need authentication of the JoinRequest
   MUST verify RequestMAC under the per-device AppKey before any
   server-side state is altered.
