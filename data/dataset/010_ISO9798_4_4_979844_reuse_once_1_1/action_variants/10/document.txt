             Mutual Challenge-Response Entity Authentication
                       draft-famed-iso979844-00


Abstract

   This document specifies a four-pass mutual challenge-response
   entity authentication mechanism in the style of ISO/IEC 9798-4
   Mechanism 4, in which the two parties share a symmetric long-term
   key and authenticate each other through a pair of message
   authentication codes that bind the exchanged challenges and the
   identifier of the responder.  The Responder's authentication
   tag binds an additional fixed protocol-stage marker
   "mac2_tag".

1.  Introduction

   This document defines a mutual entity authentication protocol
   between an Initiator role A and a Responder role B that share a
   symmetric long-term key kAB.  The MAC carried in the Responder's
   authentication token binds an additional fixed protocol-stage
   marker carrying the literal value "mac2_tag" alongside the
   exchanged challenges.  Both parties recompute the MAC over the
   same input tuple.

   The mechanism follows the structure of ISO/IEC 9798-4 Mechanism 4
   [ISO9798-4].

   The Initiator's random source is permitted to emit a single
   duplicate challenge value at most once during its lifetime.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   IdA, IdB     Public identifiers of the Initiator and Responder.
   kAB          Symmetric long-term key shared by IdA and IdB.
   RA, RB       Random challenges issued by IdA and IdB.
   "mac2_tag"   Fixed protocol-stage marker bound under the
                Responder's MAC input tuple.
   Text1..5     Opaque payload fields carried alongside the
                authentication tokens.
   sid1_mut_cr  Domain separation tag for the message from A to B.
   sid2_mut_cr  Domain separation tag for the message from B to A.
   mac(m, k)    Message authentication code over m under key k.


3.  Provisioning

   Before any session is established, a provisioning party fixes the
   pair (IdA, IdB) and a fresh symmetric long-term key kAB.


4.  Protocol Overview

         Initiator (A)                         Responder (B)
              |                                       |
              |              <RB, Text1>              |
              |<--------------------------------------|
              |                                       |
              | <RA, Text3,                           |
              |  <sid1_mut_cr, RA, RB, IdB, Text2>,   |
              |   mac1>                               |
              |-------------------------------------->|
              |                                       |
              |        <Text5, mac2>                  |
              |<--------------------------------------|

      where
        mac1 = mac(<sid1_mut_cr, RA, RB, IdB>, kAB)
        mac2 = mac(<sid2_mut_cr, RB, RA, "mac2_tag">, kAB)


5.  Message Format

      struct {
          opaque  RB;
          opaque  Text1;
      } Challenge1;

      struct {
          opaque  RA;
          opaque  Text3;
          opaque  Tagged1[];
          opaque  RequestMAC;
      } TokenAB;

      struct {
          opaque  Text5;
          opaque  ResponseMAC;    /* mac(<sid2_mut_cr, RB, RA,
                                         "mac2_tag">, kAB)      */
      } TokenBA;


6.  Processing Rules

   1.  The Responder draws fresh values RB and Text1 and emits
       Challenge1 = <RB, Text1>.

   2.  Upon receiving Challenge1, the Initiator obtains a
       challenge RA from its random source, draws fresh Text2 and
       Text3, computes mac1, and emits TokenAB.

   3.  Upon receiving TokenAB, the Responder verifies that the
       carried RequestMAC matches mac1 under kAB and the locally
       retained RB.  When the comparison succeeds, the Responder
       draws fresh Text4 and Text5, computes
       mac2 = mac(<sid2_mut_cr, RB, RA, "mac2_tag">, kAB), and
       emits TokenBA.

   4.  Upon receiving TokenBA, the Initiator verifies that the
       carried ResponseMAC matches mac2 under kAB and the locally
       retained RA.  When the comparison succeeds, the Initiator
       declares the session authenticated in both directions.


7.  Security Considerations

   The mechanism is designed to authenticate two parties to each
   other under the assumption that the long-term key kAB is known
   only to IdA and IdB.  The two domain separation tags ensure
   that a token computed for one direction cannot be reinterpreted
   as a token for the other direction.  Binding RB and IdB inside
   the Initiator's authentication token, and binding RA, RB, and
   the protocol-stage marker "mac2_tag" inside the Responder's
   authentication token, prevents an attacker from substituting
   either challenge or the identifier of the intended Responder
   without invalidating the corresponding MAC.

   The marker "mac2_tag" is a public, fixed value.  Binding it
   under the Responder's MAC input tuple offers no additional
   secrecy guarantee but provides a stable signature for
   protocol-stage classification within the Initiator's MAC
   verifier.

   The Initiator's random source operates under a profile that
   permits a single duplicate challenge value during its lifetime.
   When such a duplicate occurs, two Initiator sessions can
   complete with identical (RA, RB) pairs even though only a
   single Responder session has carried the matching exchange.
   The protocol therefore does not provide injective agreement
   from the Initiator's perspective.  Implementations that need
   injective agreement from the Initiator's perspective MUST
   replace the Initiator's random source with one that emits no
   duplicate challenge values.

   The mechanism does not protect against compromise of kAB.
