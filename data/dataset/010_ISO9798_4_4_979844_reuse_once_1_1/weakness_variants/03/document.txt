             Mutual Challenge-Response Entity Authentication
                       draft-famed-iso979844-00


Abstract

   This document specifies a four-pass mutual challenge-response
   entity authentication mechanism in the style of ISO/IEC 9798-4
   Mechanism 4, in which the two parties share a symmetric long-term
   key and authenticate each other through a pair of message
   authentication codes that bind the exchanged challenges and the
   identifier of the responder.  The Responder accepts the
   Initiator's authentication frame on the basis of its layout
   alone and does not consult any message authentication code on
   the second pass.

1.  Introduction

   This document defines a mutual entity authentication protocol
   between an Initiator role A and a Responder role B that share a
   symmetric long-term key kAB.  On the second pass, the Responder
   parses the inbound frame for an RA and a Text3 field and
   proceeds to its own emission step without verifying any message
   authentication code.

   The mechanism follows the structure of ISO/IEC 9798-4 Mechanism 4
   [ISO9798-4].

   The Initiator's random source is permitted to emit a single
   duplicate challenge value at most once during its lifetime.

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL

   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   IdA, IdB     Public identifiers of the Initiator and Responder.
   kAB          Symmetric long-term key shared by IdA and IdB.
   RA, RB       Random challenges issued by IdA and IdB.
   Text1..5     Opaque payload fields carried alongside the
                authentication tokens.
   sid1_mut_cr  Domain separation tag for the message from A to B.
   sid2_mut_cr  Domain separation tag for the message from B to A.
   mac(m, k)    Message authentication code over m under key k.


3.  Provisioning

   Before any session is established, a provisioning party fixes the
   pair (IdA, IdB) and a fresh symmetric long-term key kAB.


4.  Protocol Overview

         Initiator (A)                         Responder (B)
              |                                       |
              |              <RB, Text1>              |
              |<--------------------------------------|
              |                                       |
              |          <RA, Text3>                  |
              |-------------------------------------->|
              |                                       |
              |        <Text5, mac2>                  |
              |<--------------------------------------|

      where
        mac2 = mac(<sid2_mut_cr, RB, RA>, kAB)


5.  Message Format

      struct {
          opaque  RB;
          opaque  Text1;
      } Challenge1;

      struct {
          opaque  RA;
          opaque  Text3;
      } TokenAB;

      struct {
          opaque  Text5;
          opaque  ResponseMAC;
      } TokenBA;


6.  Processing Rules

   1.  The Responder draws fresh values RB and Text1 and emits
       Challenge1 = <RB, Text1>.

   2.  Upon receiving Challenge1, the Initiator draws a fresh
       challenge RA from its random source, draws fresh Text2 and
       Text3, and emits TokenAB = <RA, Text3>.

   3.  Upon receiving TokenAB, the Responder accepts the leading
       RA and Text3 fields without consulting any message
       authentication code.  The Responder draws fresh Text4 and
       Text5, computes mac2 = mac(<sid2_mut_cr, RB, RA>, kAB),
       and emits TokenBA.

   4.  Upon receiving TokenBA, the Initiator verifies that the
       carried ResponseMAC matches mac2 under kAB and the locally
       retained RA.  When the comparison succeeds, the Initiator
       declares the session authenticated in the
       Responder-to-Initiator direction.


7.  Security Considerations

   The Responder accepts an inbound TokenAB on the basis of its
   layout alone.  Any party that can transmit a frame carrying
   two opaque fields induces the Responder to commit on the
   leading RA value and to emit a fresh TokenBA, regardless of
   whether the matching Initiator has run.  The protocol
   therefore does not provide weak agreement, non-injective
   agreement, or injective agreement from the Responder's
   perspective: the Responder's commitments on (RA, RB) pairs
   carry no guarantee that any Initiator has been running the
   protocol at all.

   Implementations that need any agreement guarantee from the
   Responder's perspective MUST verify a message authentication
   code over the inbound TokenAB before any server-side state is
   altered.

   The Initiator's random source operates under a profile that
   permits a single duplicate challenge value during its lifetime.
   When such a duplicate occurs, two Initiator sessions can
   complete with identical (RA, RB) pairs.  The protocol
   therefore does not provide injective agreement from the
   Initiator's perspective.

   The mechanism does not protect against compromise of kAB.
