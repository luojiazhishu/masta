             Mutual Challenge-Response Entity Authentication
                       draft-famed-iso979844-00


Abstract

   This document specifies a four-pass mutual challenge-response
   entity authentication mechanism in the style of ISO/IEC 9798-4
   Mechanism 4, in which the two parties share a symmetric long-term
   key and authenticate each other through a pair of message
   authentication codes that bind the exchanged challenges and the
   identifier of the responder.  The Initiator accepts the
   Responder's final frame on the basis of its layout alone and
   does not consult any message authentication code on the third
   pass.

1.  Introduction

   This document defines a mutual entity authentication protocol
   between an Initiator role A and a Responder role B that share a
   symmetric long-term key kAB.  On the third pass, the Initiator
   parses the inbound frame for a single Text5 field and commits
   the session without verifying any message authentication code.

   The mechanism follows the structure of ISO/IEC 9798-4 Mechanism 4
   [ISO9798-4].

   The Initiator's random source is permitted to emit a single
   duplicate challenge value at most once during its lifetime.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   IdA, IdB     Public identifiers of the Initiator and Responder.
   kAB          Symmetric long-term key shared by IdA and IdB.
   RA, RB       Random challenges issued by IdA and IdB.
   Text1..5     Opaque payload fields carried alongside the
                authentication tokens.
   sid1_mut_cr  Domain separation tag for the message from A to B.
   sid2_mut_cr  Domain separation tag for the message from B to A.
   mac(m, k)    Message authentication code over m under key k.


3.  Provisioning

   Before any session is established, a provisioning party fixes the
   pair (IdA, IdB) and a fresh symmetric long-term key kAB.


4.  Protocol Overview

         Initiator (A)                         Responder (B)
              |                                       |
              |              <RB, Text1>              |
              |<--------------------------------------|
              |                                       |
              | <RA, Text3,                           |
              |  <sid1_mut_cr, RA, RB, IdB, Text2>,   |
              |   mac1>                               |
              |-------------------------------------->|
              |                                       |
              |              <Text5>                  |
              |<--------------------------------------|

      where
        mac1 = mac(<sid1_mut_cr, RA, RB, IdB>, kAB)


5.  Message Format

      struct {
          opaque  RB;
          opaque  Text1;
      } Challenge1;

      struct {
          opaque  RA;
          opaque  Text3;
          opaque  Tagged1[];
          opaque  RequestMAC;
      } TokenAB;

      struct {
          opaque  Text5;
      } TokenBA;


6.  Processing Rules

   1.  The Responder draws fresh values RB and Text1 and emits
       Challenge1 = <RB, Text1>.

   2.  Upon receiving Challenge1, the Initiator draws a fresh
       challenge RA from its random source, draws fresh Text2 and
       Text3, computes mac1, and emits TokenAB.

   3.  Upon receiving TokenAB, the Responder verifies that the
       carried RequestMAC matches mac1 under kAB and the locally
       retained RB.  When the comparison succeeds, the Responder
       draws fresh Text4 and Text5 and emits TokenBA = <Text5>.

   4.  Upon receiving TokenBA, the Initiator accepts the leading
       Text5 field without consulting any message authentication
       code and declares the session authenticated.


7.  Security Considerations

   The Initiator accepts an inbound TokenBA on the basis of its
   layout alone.  Any party that can transmit a frame carrying a
   single opaque field induces the Initiator to commit on its
   locally retained (RA, RB) values, regardless of whether the
   matching Responder has issued a TokenBA.  The protocol
   therefore does not provide non-injective agreement from the
   Initiator's perspective: an Initiator commitment may exist
   without any matching Responder run on the same (RA, RB)
   pair.

   Implementations that need any agreement guarantee from the
   Initiator's perspective MUST verify a message authentication
   code over the inbound TokenBA before declaring the session
   authenticated.

   The Initiator's random source operates under a profile that
   permits a single duplicate challenge value during its
   lifetime.

   The mechanism does not protect against compromise of kAB.
