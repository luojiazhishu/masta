             Mutual Challenge-Response Entity Authentication
                       draft-famed-iso979844-00


Abstract

   This document specifies a four-pass mutual challenge-response
   entity authentication mechanism in the style of ISO/IEC 9798-4
   Mechanism 4, in which the two parties share a symmetric long-term
   key and authenticate each other through a pair of message
   authentication codes that bind the exchanged challenges and the
   identifier of the responder.  The Initiator's authentication
   tag binds the responder challenge and identifier but does not
   bind the Initiator's own challenge.

1.  Introduction

   This document defines a mutual entity authentication protocol
   between an Initiator role A and a Responder role B that share a
   symmetric long-term key kAB.  The MAC carried in the
   Initiator's authentication token is computed over the
   Responder's challenge RB and the Responder identifier IdB
   under kAB.  The Initiator's own challenge RA is carried in the
   wire frame as a separate field and is not bound under the MAC.

   The mechanism follows the structure of ISO/IEC 9798-4 Mechanism 4
   [ISO9798-4].

   The Initiator's random source is permitted to emit a single
   duplicate challenge value at most once during its lifetime.

   kAB          Symmetric long-term key shared by IdA and IdB.
   RA, RB       Random challenges issued by IdA and IdB.
   Text1..5     Opaque payload fields carried alongside the
                authentication tokens.
   sid1_mut_cr  Domain separation tag for the message from A to B.
   sid2_mut_cr  Domain separation tag for the message from B to A.
   mac(m, k)    Message authentication code over m under key k.


3.  Provisioning

   Before any session is established, a provisioning party fixes the
   pair (IdA, IdB) and a fresh symmetric long-term key kAB.


4.  Protocol Overview

         Initiator (A)                         Responder (B)
              |                                       |
              |              <RB, Text1>              |
              |<--------------------------------------|
              |                                       |
              | <RA, Text3,                           |
              |  <sid1_mut_cr, RA, RB, IdB, Text2>,   |
              |   mac1>                               |
              |-------------------------------------->|
              |                                       |
              |        <Text5, mac2>                  |
              |<--------------------------------------|

      where
        mac1 = mac(<sid1_mut_cr, RB, IdB>, kAB)
        mac2 = mac(<sid2_mut_cr, RB, RA>, kAB)


5.  Message Format

      struct {
          opaque  RB;
          opaque  Text1;
      } Challenge1;

      struct {
          opaque  RA;
          opaque  Text3;
          opaque  Tagged1[];
          opaque  RequestMAC;     /* mac(<sid1_mut_cr, RB, IdB>,
                                         kAB)                   */
      } TokenAB;

      struct {
          opaque  Text5;
          opaque  ResponseMAC;
      } TokenBA;


6.  Processing Rules

   1.  The Responder draws fresh values RB and Text1 and emits
       Challenge1 = <RB, Text1>.

   2.  Upon receiving Challenge1, the Initiator draws a fresh
       challenge RA from its random source, draws fresh Text2
       and Text3, computes
       mac1 = mac(<sid1_mut_cr, RB, IdB>, kAB), and emits
       TokenAB.

   3.  Upon receiving TokenAB, the Responder verifies that the
       carried RequestMAC matches mac1 under kAB and the locally
       retained RB.  When the comparison succeeds, the Responder
       draws fresh Text4 and Text5, computes
       mac2 = mac(<sid2_mut_cr, RB, RA>, kAB), and emits
       TokenBA.

   4.  Upon receiving TokenBA, the Initiator verifies that the
       carried ResponseMAC matches mac2 under kAB and the locally
       retained RA.  When the comparison succeeds, the Initiator
       declares the session authenticated in both directions.


7.  Security Considerations

   The mechanism is designed to authenticate two parties to each
   other under the assumption that the long-term key kAB is known
   only to IdA and IdB.  The MAC carried in the Initiator's
   authentication token binds RB and IdB under kAB but does not
   bind the Initiator's own challenge RA.  Implementations should
   be aware that an attacker can capture the MAC carried in a
   single Initiator session and replay it alongside an arbitrary
   RA' in a fresh inbound frame to the Responder.  The Responder
   accepts the MAC because RB and IdB still match the locally
   retained values, and proceeds to commit on (RA', RB).  The
   matching Initiator has not run with the substituted challenge
   RA'; the protocol therefore does not provide non-injective
   agreement, weak agreement, or injective agreement from the
   Responder's perspective on the (RA, RB) pair.

   Implementations that need agreement on the Initiator's
   challenge MUST bind RA inside the Initiator's MAC input tuple.

   The Initiator's random source operates under a profile that
   permits a single duplicate challenge value during its
   lifetime.

   The mechanism does not protect against compromise of kAB.
