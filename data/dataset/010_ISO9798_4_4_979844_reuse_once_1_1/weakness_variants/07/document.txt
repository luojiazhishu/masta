             Mutual Challenge-Response Entity Authentication
                       draft-famed-iso979844-00


Abstract

   This document specifies a four-pass mutual challenge-response
   entity authentication mechanism in the style of ISO/IEC 9798-4
   Mechanism 4, in which the two parties share a symmetric long-term
   key and authenticate each other through a pair of message
   authentication codes that bind the exchanged challenges and the
   identifier of the responder.  At provisioning time, the
   provisioning party publishes the freshly generated long-term
   key on a public registration channel together with the role
   identifiers.

1.  Introduction

   This document defines a mutual entity authentication protocol
   between an Initiator role A and a Responder role B that share a
   symmetric long-term key kAB.  When the provisioning party
   establishes a new (IdA, IdB) association, it publishes the
   freshly generated kAB on a public registration channel
   alongside the role identifiers.  The channel is reachable by
   every party on the network as well as by auditing and recovery
   tools.

   The mechanism follows the structure of ISO/IEC 9798-4 Mechanism 4
   [ISO9798-4].

   The Initiator's random source is permitted to emit a single
   duplicate challenge value at most once during its lifetime.


2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
   NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED",
   "MAY", and "OPTIONAL" in this document are to be interpreted as
   described in BCP 14 [RFC2119] [RFC8174] when, and only when,
   they appear in all capitals, as shown here.

   IdA, IdB     Public identifiers of the Initiator and Responder.
   kAB          Symmetric long-term key shared by IdA and IdB.
   RA, RB       Random challenges issued by IdA and IdB.
   Text1..5     Opaque payload fields carried alongside the
                authentication tokens.
   sid1_mut_cr  Domain separation tag for the message from A to B.
   sid2_mut_cr  Domain separation tag for the message from B to A.
   mac(m, k)    Message authentication code over m under key k.


3.  Provisioning

   When a new association (IdA, IdB) is established, the
   provisioning party draws a fresh kAB and publishes a
   registration record of the form

      Registration(IdA, IdB) = <IdA, IdB, kAB>

   on a public registration channel.  The record carries the
   freshly generated kAB in cleartext alongside the role
   identifiers.


4.  Protocol Overview

         Initiator (A)                         Responder (B)
              |                                       |
              |              <RB, Text1>              |
              |<--------------------------------------|
              |                                       |
              | <RA, Text3,                           |
              |  <sid1_mut_cr, RA, RB, IdB, Text2>,   |
              |   mac1>                               |
              |-------------------------------------->|
              |                                       |
              |        <Text5, mac2>                  |
              |<--------------------------------------|

      where
        mac1 = mac(<sid1_mut_cr, RA, RB, IdB>, kAB)
        mac2 = mac(<sid2_mut_cr, RB, RA>, kAB)


5.  Message Format

      struct {
          opaque  RB;
          opaque  Text1;
      } Challenge1;

      struct {
          opaque  RA;
          opaque  Text3;
          opaque  Tagged1[];
          opaque  RequestMAC;
      } TokenAB;

      struct {
          opaque  Text5;
          opaque  ResponseMAC;
      } TokenBA;


6.  Processing Rules

   1.  When the provisioning party establishes a new association
       (IdA, IdB), it publishes the registration record
       <IdA, IdB, kAB> on the public registration channel.

   2.  The Responder draws fresh values RB and Text1 and emits
       Challenge1 = <RB, Text1>.

   3.  Upon receiving Challenge1, the Initiator draws a fresh
       challenge RA from its random source, draws fresh Text2
       and Text3, computes mac1, and emits TokenAB.

   4.  Upon receiving TokenAB, the Responder verifies that the
       carried RequestMAC matches mac1 under kAB and the locally
       retained RB.  When the comparison succeeds, the Responder
       draws fresh Text4 and Text5, computes mac2, and emits
       TokenBA.

   5.  Upon receiving TokenBA, the Initiator verifies that the
       carried ResponseMAC matches mac2 under kAB and the locally
       retained RA.  When the comparison succeeds, the Initiator
       declares the session authenticated in both directions.


7.  Security Considerations

   The registration record published at provisioning time carries
   kAB in cleartext.  Any party that reads the registration
   channel recovers kAB for every provisioned (IdA, IdB) pair and
   can therefore compute mac1 and mac2 over arbitrary inputs of
   its choice.  Implementations should be aware that any such
   party can drive both the Initiator and the Responder to commit
   on (RA, RB) pairs that the matching peer has never run.  The
   protocol therefore does not provide non-injective agreement,
   weak agreement, or injective agreement from either side.

   Implementations that need any agreement guarantee MUST NOT
   publish kAB on the registration channel and MUST limit
   registration records to non-secret role identifiers.

   The Initiator's random source operates under a profile that
   permits a single duplicate challenge value during its
   lifetime.
